# Research: Непрерывный ход оценки

## Исходное поведение

- Registry API хранит только статус/этап в памяти и отдаёт `/api/evaluation/progress/{id}`.
- Remote evaluator получает job ID и опрашивает внешний runner только на `queued`, `running`, `succeeded`, `failed`.
- Pipeline запускает области backend/frontend параллельно и пишет атомарный частичный team-файл после завершения каждой области.
- Registry API уже знает активный `jobID` и читает частичный файл только из текущего `runs/<jobID>`; старые результаты отсекаются по времени запуска.
- Scanner знает количество включённых файлов, исключения и ограничения снимка до запроса модели.
- Провайдер возвращает целый валидированный отчёт области, а не события по метрикам. Валидированные находки уже содержат проверяемые пути и строки.
- Страница команды при отсутствии первого частичного team-файла показывает только пустое состояние pending. Рейтинг делает ссылкой название команды, но отдельный статус не ведёт к живому прогрессу.

## Архитектурные решения

1. Сохранять журнал текущего прогона атомарным snapshot-файлом внутри его output directory. Registry API уже располагает активным job ID и тем же путём, который используется для частичного отчёта.
2. Использовать отдельный JSON Schema для операционного прогресса и генерировать Go/TypeScript-типы тем же контрактным скриптом. Не менять JSON Schema оценочного отчёта 001.
3. Описывать границы фактической наблюдаемости: область может быть `running`, но отдельная метрика остаётся `queued` до публикации валидного отчёта целой области. Не симулировать токены, инструменты или вывод модели.
4. Журнал хранит не более 20 записей на команду. В записи допускаются только статический тип события, безопасный короткий текст, timestamp, area и проверенная ссылка на finding.
5. При неизвестных или старых данных API сохраняет coarse stage. UI показывает последнее серверное состояние и понятную ошибку обновления.

## Проверенные ограничения

- Оценки read-only; прогресс не добавляет операций изменения отчётов.
- Частичные результаты доступны только после валидации/обогащения полного отчёта области.
- Файлы с чувствительными именами, исключённые артефакты и содержимое файлов нельзя переносить в события.
- Runner API не обязан передавать событийную ленту по сети: события записывает существующий pipeline в job output, который уже совместно читают runner и Registry API.
