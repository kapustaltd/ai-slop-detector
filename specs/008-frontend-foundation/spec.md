# Feature Specification: Каркас фронтенд-приложения

**Feature Branch**: `008-frontend-foundation`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "Подготовительный этап: заложить базу фронтенд-приложения — определиться с библиотеками, UI-китом, архитектурой (FSD) и поставить работающий каркас."

## Overview

Подготовительный этап перед 005 и 006: собрать пустое, но работающее приложение, в котором уже
решены все сквозные вопросы — сборка, маршрутизация, доступ к данным, UI-кит, архитектурные
границы, типы из схем, линт и тесты. Дальше страницы рейтинга и команды строятся внутри готового
каркаса, а не вместе с ним.

Фича не даёт пользовательской ценности напрямую: её потребитель — разработчик. Поэтому критерии
приёмки сформулированы через то, что разработчик может сделать, а не через то, что видит жюри.

## Clarifications

### Session 2026-09-22

- Q: Макеты задают подсветку кода на этапе сборки и отсутствие Shiki в рантайме. Меняем? → A:
  нет. Shiki остаётся в рантайме с ленивой загрузкой (FR-019); из макетов берутся только цвета
  подсветки.
- Q: Где живут дизайн-токены? → A: `src/app/styles/globals.css`, с префиксом `--ds-`;
  `src/index.css` остаётся файлом shadcn и только переназначает его семантические переменные.
- Q: Куда попадают компоненты shadcn и куда собственные? → A: shadcn — в
  `src/shared/ui/shadcn` (вне линтера), собственные компоненты дизайн-системы — в
  `src/shared/ui`.

### Session 2026-09-21

- Q: Какой UI-кит? → A: shadcn/ui + Tailwind + Radix. Компоненты живут в репозитории и правятся
  как обычный код; готовый кит вроде Mantine или Ant Design не берём.
- Q: Как приложение получает данные? → A: импортом на сборке из каталога дата-бандла, ленивыми
  чанками на команду. Рантайм-загрузки, состояний «грузится/ошибка сети» и повтора нет.
- Q: Нужен ли TanStack Query? → A: нет. Серверного состояния в системе нет.
- Q: Какая маршрутизация? → A: React Router в hash-режиме — ссылки с фильтрами и адресуемые узлы
  работают на любом статическом хостинге без правил переписывания.
- Q: Линт и формат? → A: ESLint + Prettier (не Biome) — богаче плагины, в частности a11y и
  react-hooks.
- Q: Архитектура? → A: Feature-Sliced Design; слой `features` не заводится, пока не появится
  переиспользуемая между виджетами функциональность.
- Q: Подсветка кода? → A: Shiki, ленивой загрузкой, только нужные языки.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Разработчик запускает приложение одной командой (Priority: P1)

Разработчик клонирует репозиторий, ставит зависимости, запускает dev-сервер и видит работающее
приложение с фикстурным дата-бандлом.

**Why this priority**: без этого нельзя начать 005 и 006.

**Independent Test**: выполнить установку и запуск на чистой машине по README и получить
открывающееся приложение.

**Acceptance Scenarios**:

1. **Given** чистый клон репозитория, **When** разработчик выполняет установку и запуск по
   README, **Then** приложение открывается в браузере без ошибок в консоли.
2. **Given** запущенное приложение, **When** открывается корневой маршрут, **Then** отображается
   страница-заглушка рейтинга с данными из фикстурного бандла.
3. **Given** запущенное приложение, **When** разработчик правит компонент, **Then** изменение
   видно без перезагрузки страницы.
4. **Given** чистый клон, **When** выполняется production-сборка, **Then** она проходит без
   ошибок и выдаёт статические файлы, открываемые с файловой системы или любого статического
   хостинга.

---

### User Story 2 - Данные приходят типизированными из схем (Priority: P1)

Разработчик обращается к данным бандла через один модуль доступа и получает типы, сгенерированные
из JSON Schema, а не написанные руками.

**Why this priority**: принцип IX конституции; без этого контракт и код разойдутся в первый же
день.

**Independent Test**: изменить схему, перегенерировать типы и убедиться, что несоответствие в коде
ломает проверку типов.

**Acceptance Scenarios**:

1. **Given** схемы контракта 001 и дата-бандла 004, **When** запускается генерация типов, **Then**
   TypeScript-типы создаются без ошибок и попадают в репозиторий.
2. **Given** схема изменена, а типы не перегенерированы, **When** запускается проверка, **Then**
   она падает с указанием на расхождение.
3. **Given** приложение, **When** разработчик ищет, откуда берутся данные, **Then** все обращения
   к бандлу идут через один модуль доступа.
4. **Given** модуль доступа, **When** потребуется перейти с импорта на сборке на загрузку в
   рантайме, **Then** правка затрагивает только этот модуль.
5. **Given** бандл с несколькими командами, **When** собирается приложение, **Then** файл каждой
   команды попадает в отдельный чанк и не грузится на странице рейтинга.

---

### User Story 3 - Архитектурные границы проверяются машиной (Priority: P2)

Разработчик не может случайно импортировать из вышележащего слоя или влезть во внутренности
чужого среза — это ловится линтером, а не ревью.

**Why this priority**: архитектура, которую никто не проверяет, перестаёт существовать на третий
день хакатона.

**Independent Test**: намеренно написать запрещённый импорт и убедиться, что проверка падает.

**Acceptance Scenarios**:

1. **Given** код с импортом из вышележащего слоя, **When** запускается линт, **Then** он падает с
   понятным сообщением.
2. **Given** код с импортом внутренностей чужого среза в обход его публичного API, **When**
   запускается линт, **Then** он падает.
3. **Given** корректный код, **When** запускается линт, **Then** он проходит без предупреждений.

---

### User Story 4 - Готовая основа для оформления (Priority: P2)

Разработчик берёт компоненты UI-кита из репозитория, а не подключает чужую библиотеку, и получает
согласованную светлую и тёмную темы.

**Why this priority**: определяет скорость сборки 005 и 006 и внешний вид инструмента.

**Independent Test**: добавить компонент кита и использовать его на странице-заглушке в обеих
темах.

**Acceptance Scenarios**:

1. **Given** каркас, **When** разработчик добавляет компонент UI-кита, **Then** его исходный код
   появляется в репозитории и правится как обычный код.
2. **Given** приложение, **When** переключается тема, **Then** и компоненты, и графики, и
   подсветка кода читаемы в обеих темах.
3. **Given** страница-заглушка, **When** она открыта на экране шириной 360 px, **Then** вёрстка не
   ломается.

---

### User Story 5 - Тесты и проверки запускаются одной командой (Priority: P2)

Разработчик перед коммитом запускает одну команду и видит результат линта, типов и тестов.

**Why this priority**: принцип VIII конституции; дешевле договориться об этом сразу, чем
прикручивать в конце.

**Independent Test**: запустить проверки на чистом каркасе и получить зелёный результат.

**Acceptance Scenarios**:

1. **Given** каркас, **When** запускается проверка, **Then** последовательно выполняются
   генерация/сверка типов, линт, проверка типов и тесты.
2. **Given** сломанный тест, **When** запускается проверка, **Then** она падает с указанием на
   тест.
3. **Given** каркас, **When** запускаются тесты, **Then** присутствует хотя бы один тест,
   проверяющий отрисовку страницы-заглушки на фикстурном бандле.

---

### Edge Cases

- Фикстурный бандл отсутствует или пуст → сборка даёт понятную ошибку, а не падает внутри Vite с
  невнятным сообщением.
- Бандл содержит версию схемы новее, чем понимает приложение → приложение показывает явное
  предупреждение о несовместимости.
- В бандле есть команда без файла деталей → обращение к ней даёт контролируемую ошибку данных.
- Язык сниппета неизвестен подсветке → код показывается простым текстом с номерами строк.
- Приложение открыто по прямой ссылке на несуществующий маршрут → показывается страница «не
  найдено», а не пустой экран.

## Requirements *(mandatory)*

### Functional Requirements

#### Сборка и запуск

- **FR-001**: Приложение MUST собираться в статические файлы, открываемые без сервера приложений.
- **FR-002**: Репозиторий MUST содержать инструкцию запуска: установка, dev-режим, сборка,
  проверки.
- **FR-003**: Маршрутизация MUST работать в hash-режиме, чтобы прямые ссылки открывались на любом
  статическом хостинге.
- **FR-004**: Приложение MUST иметь страницу «не найдено» для неизвестных маршрутов.

#### Данные и типы

- **FR-005**: Данные дата-бандла MUST подключаться импортом на этапе сборки; рантайм-загрузки
  данных MUST NOT быть.
- **FR-006**: Все обращения к данным MUST идти через единственный модуль доступа в `shared/api`.
- **FR-007**: Файл каждой команды MUST попадать в отдельный чанк и не загружаться на странице
  рейтинга.
- **FR-008**: TypeScript-типы данных MUST генерироваться из JSON Schema контракта 001 и
  дата-бандла 004; ручные дубли типов MUST NOT попадать в репозиторий.
- **FR-009**: Проверка актуальности сгенерированных типов MUST входить в общую проверку и падать
  при расхождении.
- **FR-010**: Приложение MUST проверять версию схемы бандла и явно сообщать о несовместимости.
- **FR-011**: Приложение MUST NOT вычислять баллы, места и агрегаты — только отображать значения
  из бандла (принцип VI конституции).
- **FR-012**: Приложение MUST оставаться read-only: операций записи MUST NOT быть (принцип V).

#### Архитектура

- **FR-013**: Код MUST быть организован по Feature-Sliced Design со слоями `app`, `pages`,
  `widgets`, `entities`, `shared`.
- **FR-014**: Каждый срез MUST иметь публичный API; импорт внутренностей чужого среза MUST
  отвергаться линтером.
- **FR-015**: Импорты MUST идти только вниз по слоям; нарушение MUST ломать проверку.
- **FR-016**: Слой `features` MUST NOT заводиться до появления функциональности, переиспользуемой
  между виджетами.

#### Оформление

- **FR-017**: Компоненты UI-кита MUST лежать в репозитории и правиться как обычный код.
- **FR-018**: Приложение MUST поддерживать светлую и тёмную темы; компоненты, графики и подсветка
  кода MUST быть читаемы в обеих.
- **FR-019**: Подсветка кода MUST загружаться лениво и ограничиваться нужными языками, а при
  неизвестном языке MUST показывать простой текст с номерами строк.
- **FR-020**: Вёрстка MUST оставаться пригодной к использованию на экране шириной от 360 px.
- **FR-021**: Приложение MUST NOT обращаться к внешним сетевым ресурсам во время работы: шрифты,
  иконки и стили MUST быть локальными.

#### Проверки

- **FR-022**: Репозиторий MUST предоставлять одну команду, запускающую сверку типов, линт,
  проверку типов и тесты.
- **FR-023**: Каркас MUST содержать минимум один тест отрисовки на фикстурном бандле.
- **FR-024**: Линт MUST включать правила доступности и правила хуков React.

### Key Entities

- **Модуль доступа к данным (BundleAccess)**: единственная точка, через которую приложение
  получает индекс рейтинга, данные команды, рубрику и статистику.
- **Фикстурный бандл (FixtureBundle)**: набор JSON-файлов для разработки и тестов, совпадающий по
  структуре с рабочим.
- **Сгенерированные типы (GeneratedTypes)**: TypeScript-типы, полученные из схем 001 и 004.
- **Срез (FSD Slice)**: единица кода с публичным API внутри слоя.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Разработчик на чистой машине по README поднимает приложение не более чем за 10
  минут.
- **SC-002**: Запрещённый импорт между слоями ловится проверкой в 100% случаев.
- **SC-003**: Расхождение типов со схемой ломает проверку в 100% случаев.
- **SC-004**: Страница рейтинга не загружает данные отдельных команд — проверяется составом
  чанков сборки.
- **SC-005**: Приложение работает без единого сетевого запроса к сторонним доменам.
- **SC-006**: Одна команда проверки даёт зелёный результат на чистом каркасе.
- **SC-007**: Каркас готов к тому, чтобы 005 и 006 добавляли страницы, не трогая настройку
  сборки, маршрутизации и доступа к данным.

## Assumptions

- Стек зафиксирован владельцем продукта: Vite, React, TypeScript, shadcn/ui, Tailwind, Radix,
  TanStack Table, Recharts, Shiki, React Router (hash), ESLint, Prettier, Vitest.
- Приложение живёт в каталоге `web/`; фикстурный и рабочий бандлы лежат в `web/data/` — не в
  `public/`, потому что оттуда Vite копирует файлы как есть, без обработки и разбиения на чанки.
- Интерфейс на русском языке, один язык, библиотека локализации не нужна.
- Глобальный стейт-менеджер не нужен: состояние таблицы живёт в адресе страницы.
- Данные статичны после прогона пайплайна, поэтому обновление данных означает пересборку
  приложения.

## Dependencies

- **001-evaluation-contract**: схема отчёта — источник типов.
- **004-data-bundle**: структура бандла — источник типов и раскладки файлов.
- Блокирует: **005-leaderboard**, **006-team-details**.
