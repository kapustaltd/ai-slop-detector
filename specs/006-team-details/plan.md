# Implementation Plan: Страница команды — графики и drill-down

**Branch**: `006-team-details` | **Date**: 2026-09-22 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/006-team-details/spec.md`

## Summary

Как и 005: страница уже работает функционально (radar/bar-графики на recharts, drill-down через
`<details>`, подсветка кода на Shiki в рантайме, фильтры находок в адресе), но вся вёрстка —
дефолты shadcn/Tailwind без токенов, и вся логика лежит в одном файле `team-page.tsx` (659 строк) с
компонентами `Snippet`/`FindingCard`/`MetricDetails`/`AreaCharts`/`AreaBreakdown` внутри него. Эта
фича — переделка вёрстки под макеты `04-06` и разбор по FSD (`entities/metric`, `entities/finding`,
несколько `widgets`), плюс достройка четырёх оставшихся компонентов инвентаря: `TaxonomyRow`,
`AnchorScale`, `FindingCard`, `SeverityBar`. Данные и большая часть логики (подсветка кода, фильтры,
подсчёт находок) переносятся почти как есть — переписывается представление, не пайплайн.

## Technical Context

**Language/Version**: TypeScript 5, React 19 (спека 008), общий стек с 005

**Primary Dependencies**: `recharts` (radar/bar — уже используется), `shiki` (подсветка кода в
рантайме — design-deviations.md, пункт 1; уже работает в текущем `team-page.tsx`, переносится, а не
переписывается), `react-router-dom` 7, Tailwind v4 токены

**Storage**: N/A — статический бандл (`loadTeam`, `loadRubric`, `getStats`, все уже есть в
`shared/api/bundle.ts`); дополнительно для «места в рейтинге» и prev/next — синхронный
`getLeaderboardIndex()` (005), без нового похода за данными

**Testing**: Vitest + Testing Library, запросы по роли/тексту

**Target Platform**: тот же статичный SPA, вёрстка от 360 px

**Project Type**: web (frontend-only, FSD)

**Performance Goals**: SC-001 — путь «категория → метрика → код» за минуту; подсветка кода не
должна блокировать первый рендер (уже асинхронная в текущей реализации — `useEffect` на
`highlighterFactoryPromise`, шаблон переносится)

**Constraints**: read-only (FR-020b), UI не пересчитывает баллы/веса/вклады (FR-005, принцип VI) —
только показывает то, что уже в `TeamBundle`/`StatsBundle`; сниппет кода не подменяет ответ модели
содержимым файла (FR-013, принцип «код команд — данные»)

**Scale/Scope**: один `TeamBundle` на страницу; таксономия — до 8 категорий × ~2 подкатегории × до
27 метрик на область (backend), меньше на frontend; находок на метрику — по факту метрики 001
FR (не ограничено жёстко, UI должен оставаться читаемым при 7+ находках на метрику — см. Edge Cases
спеки и DESIGN.md «по умолчанию раскрыта одна находка»)

**Structure Decision**: `entities/metric` и `entities/finding` — два отдельных среза, а не один
`entities/metric` со всем внутри: `Metric` и `Finding` — разные существительные предметной области
(метрика содержит находки, но выставление балла и структура находки живут по разным правилам
рубрики/конституции), и `FindingCard`/`SeverityBar` используются `findings-summary` независимо от
`taxonomy-tree`. Подсветка кода (`highlight-snippet.ts`) — в `entities/finding/model`, а не в
`shared/lib`: код команды — данные, привязанные к конкретной находке (принцип IV), а не общая
дизайн-система-утилита уровня `shared`. Виджетов шесть — по числу самостоятельно тестируемых блоков
макета; `features` не заводится (сортировка находок и раскрытие дерева живут внутри своих виджетов).

## Расхождения макета с FR — на ваше решение

1. **«Только слабые места»** — переключатель в макете (`04-team-light.html`) рядом с деревом
   таксономии, скрывающий узлы выше порога. Не упомянут ни в одном FR. Предлагаю не реализовывать
   сейчас (симметрично решению по 005: не расширяем объём молча).
2. **«Свернуть всё»** — явный контрол для очистки всех независимо раскрытых узлов дерева.
   Открытие соседнего узла больше не схлопывает уже открытые узлы.
3. **«Исходный JSON команды»** — ссылка внизу макета на сырой JSON. Не в FR. Предлагаю не собирать:
   это debug-возможность оператора, не жюри, и таких данных «наружу» в контракте 004 нет отдельным
   эндпоинтом — TeamBundle и так JSON-файл, доступный не через UI.
4. **Предыдущая/следующая команда** — кнопки навигации в макетах `04-06`. Не в FR-списке ни одной
   спеки (005 или 006). Реализуемо без нового похода за данными (`getLeaderboardIndex()` уже
   синхронный), но это новая функциональность страницы. Предлагаю реализовать: риск минимален (то
   же самое площадь, что уже есть в бандле), а без неё «три уровня и назад» в макете `06` (путь
   рейтинг → команда → категория → подкатегория → метрика) неудобны для просмотра нескольких
   команд подряд — сценарий, прямо упомянутый в SC-001.
5. **«Место в рейтинге N из M (делит со «Х»)»** — тоже не в явном FR, но данные уже в
   `LeaderboardTeam.rank`, вычисления не требует. Предлагаю показать — низкий риск, тот же характер
   решения, что бейдж «внутренний инструмент жюри» в 005.
6. **Ссылка на конкретную находку** (`?...&finding=f-214` в макете `06-metric-drilldown.html`) —
   FR-021 требует адресуемость узла таксономии (категория/подкатегория/метрика), не находки внутри
   метрики. У находки в контракте 001 нет поля `id` (`TeamFinding`: `kind`, `severity`, `file`,
   `line_start`, `line_end`, `title`, `explanation`, `suggestion?`, `link_status?`, `snippet?`,
   `permalink?`) — только пайплайн различает находки. Предлагаю строить на клиентском производном
   слаге (`file:line_start-line_end`, детерминирован в пределах бандла) без правки контракта —
   деталь реализации, не блокирующий вопрос; если не нужно, просто не подключаю `finding` в
   `contracts/url-params.md`.
