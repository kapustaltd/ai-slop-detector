# Feature Specification: Страница команды — графики и drill-down

**Feature Branch**: `006-team-details`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "Страница команды: radar chart по категориям с наложением медианы, bar chart команда против среднего, распределение находок, drill-down категория → подкатегория → метрика с якорями рубрики и подсвеченным кодом, метаданные прогона."

## Overview

Страница команды отвечает на вопрос «почему у нас такой балл». Сверху — профиль оценок в сравнении
с остальными командами, ниже — разбор по таксономии: категория, её подкатегории и метрики — что
оценивалось, как оценивалось, что нашли,
где именно в коде. Всё подкреплено сниппетами, вырезанными из репозитория, и постоянными ссылками.

## Clarifications

### Session 2026-09-21

- Q: На каком уровне строятся обзорные графики? → A: по категориям (8 backend / 7 frontend);
  метрики видны только в drill-down, иначе radar-график нечитаем.
- Q: Какова глубина drill-down? → A: три уровня — категория → подкатегория → метрика → находки.
- Q: Кто пользователь страницы? → A: организаторы и жюри; платформа внутренняя, доступ
  ограничивается хостингом.
- Q: Откуда страница берёт данные? → A: из статического дата-бандла (фича 004); сервера и API
  нет.
- Q: Есть ли на странице правка оценок? → A: нет, страница только показывает (принцип V
  конституции); оценка — вспомогательная метрика, решение жюри принимает вне системы.
- Q: Нужен ли график динамики оценок по ходу хакатона? → A: нет. Оценка выполняется однократным
  пакетным прогоном после дедлайна, живого рейтинга нет — страница показывает одну оценку команды.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Профиль команды в сравнении с остальными (Priority: P1)

Жюри открывает страницу команды и сразу видит, по каким категориям она сильнее или слабее
остальных: radar-график по категориям с наложенной медианой всех команд, отдельно для frontend и
backend.

**Why this priority**: даёт мгновенный ответ «где мы проседаем» — основная ценность страницы.

**Independent Test**: открыть страницу на фикстурах нескольких команд и сверить точки графика с
данными.

**Acceptance Scenarios**:

1. **Given** команда с оценками по backend, **When** открывается страница, **Then** отображается
   radar-график по 8 категориям `backend.v1` с наложенной медианой всех команд.
2. **Given** команда с оценками по обеим областям, **When** открывается страница, **Then**
   frontend и backend показаны раздельно, без смешивания таксономий разных рубрик.
3. **Given** менее двух оценённых команд, **When** строится график, **Then** медиана не рисуется,
   и это явно объяснено.
4. **Given** bar-график «команда против среднего», **When** он отображается, **Then** по каждому
   категории видно отклонение от среднего.

---

### User Story 2 - Drill-down: категория → подкатегория → метрика (Priority: P1)

Пользователь раскрывает категорию и видит её подкатегории с вычисленными баллами, раскрывает
подкатегорию и видит её метрики, раскрывает метрику и получает полную картину: балл, краткий
вывод, развёрнутое обоснование, описание метрики и якоря рубрики («как оценивается»), список
находок с подсвеченным кодом и ссылками на репозиторий.

**Why this priority**: это ядро прозрачности — принцип II конституции.

**Independent Test**: пройти путь категория → подкатегория → метрика на фикстуре и проверить
наличие всех блоков на каждом уровне.

**Acceptance Scenarios**:

1. **Given** метрика с оценкой, **When** она раскрыта, **Then** показаны балл, `summary` и
   `rationale`.
2. **Given** та же метрика, **When** пользователь смотрит блок «как оценивается», **Then**
   показаны описание метрики и якоря уровней 2/5/8/10 из рубрики той версии, по которой
   выставлена оценка.
3. **Given** находка со сниппетом, **When** она отображается, **Then** код показан с подсветкой
   синтаксиса, с номерами строк и с выделением указанного диапазона.
4. **Given** находка, **When** пользователь кликает по ссылке, **Then** открывается постоянная
   ссылка на участок кода в репозитории на зафиксированном SHA.
5. **Given** находка с непроверенной ссылкой на код, **When** она отображается, **Then** это явно
   помечено, и сниппет не подменяется текстом из ответа модели.
6. **Given** метрика с низким `confidence`, **When** она отображается, **Then** уровень
   уверенности виден пользователю.

---

### User Story 3 - Распределение находок (Priority: P2)

Пользователь видит общую картину: сколько сильных сторон и проблем найдено, как проблемы
распределены по серьёзности.

**Why this priority**: помогает расставить приоритеты по исправлениям; дополняет, но не заменяет
drill-down.

**Independent Test**: сверить подсчёты с содержимым фикстуры.

**Acceptance Scenarios**:

1. **Given** оценка с находками, **When** открывается страница, **Then** показано распределение
   `strength`/`issue` и разбивка проблем по `severity`.
2. **Given** клик по сегменту распределения, **When** он выполнен, **Then** список находок
   фильтруется соответственно.

---

### User Story 4 - Метаданные и доверие к оценке (Priority: P2)

Жюри проверяет, на каком коммите и какой версией скилла и рубрики была получена оценка, и когда.

**Why this priority**: принцип воспроизводимости; без этих данных спор с командой неразрешим.

**Independent Test**: сверить метаданные на странице с метаданными фикстуры.

**Acceptance Scenarios**:

1. **Given** завершённая оценка, **When** открывается страница, **Then** показаны SHA, версии
   скилла, рубрики, схемы, модель и время оценки.
2. **Given** SHA, **When** пользователь кликает по нему, **Then** открывается коммит в
   репозитории.
3. **Given** оценка с флагом `needs_review` или предупреждениями (`warnings`), **When**
   открывается страница, **Then** они показаны с пояснением, что это значит.
4. **Given** оценка, помеченная `needs_review` из-за разброса между прогонами, **When**
   открывается страница, **Then** видно, по каким метрикам разброс и какой он.

---

### Edge Cases

- Команда оценена только по одной области → вторая область показана как «нет данных», графики по
  ней не рисуются.
- Оценка упала → показана причина; перезапуск выполняется оператором через пайплайн, кнопки в
  интерфейсе нет.
- Критерий без находок → невозможно по контракту 001; при получении таких данных показывается
  ошибка данных, а не пустой блок.
- Очень длинный сниппет → сворачивается с возможностью раскрыть, ссылка на полный фрагмент
  сохраняется.
- Файл сниппета на языке без подсветки → показывается как обычный текст с номерами строк.
- Оценка сделана по старой версии рубрики → показываются якоря именно той версии, с пометкой о
  версии.

## Requirements *(mandatory)*

### Functional Requirements

#### Обзор и графики

- **FR-001**: Страница MUST отображать radar-график баллов по категориям отдельно для backend и
  frontend.
- **FR-002**: На radar-график MUST накладываться медиана соответствующей категории по всем
  оценённым командам.
- **FR-003**: Страница MUST отображать bar-график «команда против среднего» по каждой категории;
  метрики на обзорные графики MUST NOT выводиться — их слишком много для читаемого графика.
- **FR-004**: При недостатке данных для медианы/среднего страница MUST это явно сообщать, а
  MUST NOT рисовать вводящие в заблуждение линии.
- **FR-005**: Страница MUST отображать итоговый балл команды и баллы по областям, полученные из
  API без пересчёта на клиенте.
- **FR-006**: Графики MUST быть читаемы в обеих темах оформления и иметь текстовую альтернативу
  (значения доступны не только в виде графика).

#### Drill-down

- **FR-007**: Страница MUST позволять пройти три уровня таксономии — категория, подкатегория,
  метрика — и на уровне метрики показать балл, `summary`,
  `rationale` и уровень `confidence`.
- **FR-008**: Раскрытая метрика MUST показывать описание метрики и якоря уровней из рубрики той
  версии, которой выставлена оценка.
- **FR-009**: Страница MUST показывать находки метрики с типом (`strength`/`issue`) и
  серьёзностью.
- **FR-010**: Сниппеты кода MUST отображаться с подсветкой синтаксиса, номерами строк и
  выделением указанного диапазона.
- **FR-011**: Каждая находка MUST иметь постоянную ссылку на участок кода в репозитории на
  зафиксированном SHA.
- **FR-012**: Находки с непроверенными ссылками MUST быть явно помечены.
- **FR-013**: Страница MUST NOT показывать код, пришедший из ответа модели, как содержимое файла.
- **FR-014**: Для находок типа `issue` страница MUST показывать рекомендацию по улучшению.

#### Находки и метаданные

- **FR-015**: Страница MUST показывать распределение находок по типу и серьёзности.
- **FR-016**: Страница MUST позволять фильтровать находки по типу и серьёзности.
- **FR-017**: Страница MUST показывать метаданные: SHA, версии скилла, рубрики и схемы, модель,
  время оценки.
- **FR-018**: Страница MUST показывать предупреждения (`warnings`) и флаг `needs_review` с
  человекочитаемым пояснением.
- **FR-019**: Страница MUST показывать, что оценка — вспомогательная метрика, а не итоговое
  решение жюри, и MUST NOT подавать балл как вердикт.
- **FR-020**: Страница MUST корректно отображать состояния: загрузка, оценка выполняется, оценка
  не удалась, нет данных.
- **FR-020a**: Страница MUST показывать вычисленные баллы категорий и подкатегорий вместе с их
  весами, чтобы был виден вклад каждого узла в итог.
- **FR-020b**: Страница MUST оставаться read-only: правки баллов, комментариев и перезапуска
  оценки в интерфейсе MUST NOT быть (принцип V конституции).
- **FR-021**: Ссылка на конкретный раскрытый узел таксономии MUST быть адресуемой, чтобы её можно было
  переслать.

### Key Entities

- **Профиль команды (TeamProfile)**: баллы по категориям, подкатегориям и метрикам обеих
  областей, итоги, сравнение с
  медианой и средним.
- **Узел таксономии (TaxonomyNode)**: категория или подкатегория — название, вес, вычисленный
  балл, дочерние узлы.
- **Блок метрики (MetricPanel)**: балл, вывод, обоснование, `confidence`, описание и якоря, вес,
  находки.
- **Отображаемая находка (FindingView)**: тип, серьёзность, заголовок, объяснение, рекомендация,
  сниппет, ссылка, признак валидности ссылки.
- **Метаданные оценки (EvaluationMeta)**: SHA, версии, модель, время, предупреждения, флаги.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Член жюри за одну минуту определяет две самые слабые категории команды, спускается
  до конкретных метрик и
  находит конкретные места в коде, которые это подтверждают.
- **SC-002**: 100% находок на странице сопровождаются сниппетом из репозитория либо явной
  пометкой о непроверенной ссылке.
- **SC-003**: Для 100% метрик доступен блок «как оценивается» с якорями уровней, а для каждой
  категории и подкатегории виден её вес и вычисленный балл.
- **SC-004**: Страница полностью работает на фикстурном бандле без запуска пайплайна.
- **SC-005**: Вопрос «почему такой балл» закрывается по данным страницы без обращения к
  разработчикам платформы.
- **SC-006**: Страница остаётся пригодной к использованию на экране шириной от 360 px.

## Assumptions

- Подсветка синтаксиса выполняется на клиенте или на этапе сборки, без обращения к внешним
  сервисам.
- Медианы и средние приходят из файла статистики дата-бандла, а не считаются на клиенте.
- Страница показывает одну (последнюю) оценку команды; графика динамики нет (Q2).
- Пользователи страницы — организаторы и жюри; редактирования оценок в системе нет вовсе.
- Постоянные ссылки и сниппеты готовит пайплайн; страница их только отображает.
- Графики строятся по одной рубрике за раз — таксономии backend и frontend не смешиваются.
- Обзорные графики строятся по категориям (8 для backend, 7 для frontend); 27 и 23 метрики на
  radar-график не помещаются читаемо, поэтому метрики видны только в drill-down.
- Платформа — внутренний административный инструмент: страница доступна только организаторам и
  жюри после авторизации.

## Dependencies

- **001-evaluation-contract**: структура отчёта, рубрики, фикстуры (блокирующая).
- **004-data-bundle**: формат данных команды, рубрики и статистики.
- **003-runner-ingestion**: собирает бандл со сниппетами и постоянными ссылками.
