# Feature Specification: Страница команды — графики и drill-down

**Feature Branch**: `006-team-details`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "Страница команды: radar chart по критериям с наложением медианы, bar chart команда против среднего, распределение находок, drill-down в критерий с якорями рубрики и подсвеченным кодом, метаданные прогона."

## Overview

Страница команды отвечает на вопрос «почему у нас такой балл». Сверху — профиль оценок в сравнении
с остальными командами, ниже — разбор по критериям: что оценивалось, как оценивалось, что нашли,
где именно в коде. Всё подкреплено сниппетами, вырезанными из репозитория, и постоянными ссылками.

## Clarifications

### Session 2026-09-21

- Q: Нужен ли график динамики оценок? → A: да, режим живого рейтинга (периодические прогоны с
  историей по SHA) требует графика динамики на странице команды.
- Q: Можно ли смотреть не только последнюю оценку? → A: да, точка истории выбирается, и страница
  показывает данные именно той оценки.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Профиль команды в сравнении с остальными (Priority: P1)

Участник открывает страницу своей команды и сразу видит, по каким критериям он сильнее или слабее
остальных: radar-график по критериям с наложенной медианой всех команд, отдельно для frontend и
backend.

**Why this priority**: даёт мгновенный ответ «где мы проседаем» — основная ценность страницы.

**Independent Test**: открыть страницу на фикстурах нескольких команд и сверить точки графика с
данными.

**Acceptance Scenarios**:

1. **Given** команда с оценками по backend, **When** открывается страница, **Then** отображается
   radar-график по критериям `backend.v1` с наложенной медианой всех команд.
2. **Given** команда с оценками по обеим областям, **When** открывается страница, **Then**
   frontend и backend показаны раздельно, без смешивания критериев разных рубрик.
3. **Given** менее двух оценённых команд, **When** строится график, **Then** медиана не рисуется,
   и это явно объяснено.
4. **Given** bar-график «команда против среднего», **When** он отображается, **Then** по каждому
   критерию видно отклонение от среднего.

---

### User Story 2 - Drill-down в критерий (Priority: P1)

Пользователь раскрывает критерий и получает полную картину: балл, краткий вывод, развёрнутое
обоснование, описание критерия и якоря рубрики («как оценивается»), список находок с подсвеченным
кодом и ссылками на репозиторий.

**Why this priority**: это ядро прозрачности — принцип II конституции.

**Independent Test**: раскрыть критерий на фикстуре и проверить наличие всех блоков.

**Acceptance Scenarios**:

1. **Given** критерий с оценкой, **When** он раскрыт, **Then** показаны балл, `summary` и
   `rationale`.
2. **Given** тот же критерий, **When** пользователь смотрит блок «как оценивается», **Then**
   показаны описание критерия и якоря уровней 2/5/8/10 из рубрики той версии, по которой
   выставлена оценка.
3. **Given** находка со сниппетом, **When** она отображается, **Then** код показан с подсветкой
   синтаксиса, с номерами строк и с выделением указанного диапазона.
4. **Given** находка, **When** пользователь кликает по ссылке, **Then** открывается постоянная
   ссылка на участок кода в репозитории на зафиксированном SHA.
5. **Given** находка с непроверенной ссылкой на код, **When** она отображается, **Then** это явно
   помечено, и сниппет не подменяется текстом из ответа модели.
6. **Given** критерий с низким `confidence`, **When** он отображается, **Then** уровень
   уверенности виден пользователю.

---

### User Story 3 - Динамика оценок по ходу хакатона (Priority: P2)

Команда работает над проектом, платформа периодически переоценивает репозиторий. Участник
открывает страницу и видит, как менялись итог и баллы по областям от коммита к коммиту — видно,
помогла ли правка.

**Why this priority**: это то, ради чего включён живой рейтинг (Q2); без графика история оценок
остаётся невидимой.

**Independent Test**: подготовить фикстуры с несколькими оценками одной команды на разных SHA и
проверить график.

**Acceptance Scenarios**:

1. **Given** команда с несколькими оценками на разных SHA, **When** открывается страница, **Then**
   отображается график динамики итога и баллов по областям по времени.
2. **Given** точка графика, **When** пользователь наводит на неё, **Then** показываются SHA, время
   оценки и баллы этой точки.
3. **Given** команда с единственной оценкой, **When** открывается страница, **Then** график
   динамики не рисуется, а показывается пояснение, что точек пока недостаточно.
4. **Given** точка истории, коммит которой более недоступен (форс-пуш), **When** она отображается,
   **Then** это помечено, а точка из истории не исчезает.
5. **Given** график динамики, **When** пользователь выбирает точку, **Then** остальная часть
   страницы может быть показана для этой оценки, а не только для последней.

---

### User Story 4 - Распределение находок (Priority: P2)

Пользователь видит общую картину: сколько сильных сторон и проблем найдено, как проблемы
распределены по серьёзности.

**Why this priority**: помогает расставить приоритеты по исправлениям; дополняет, но не заменяет
drill-down.

**Independent Test**: сверить подсчёты с содержимым фикстуры.

**Acceptance Scenarios**:

1. **Given** оценка с находками, **When** открывается страница, **Then** показано распределение
   `strength`/`issue` и разбивка проблем по `severity`.
2. **Given** клик по сегменту распределения, **When** он выполнен, **Then** список находок
   фильтруется соответственно.

---

### User Story 5 - Метаданные и доверие к оценке (Priority: P2)

Жюри проверяет, на каком коммите и какой версией скилла и рубрики была получена оценка, и когда.

**Why this priority**: принцип воспроизводимости; без этих данных спор с командой неразрешим.

**Independent Test**: сверить метаданные на странице с метаданными фикстуры.

**Acceptance Scenarios**:

1. **Given** завершённая оценка, **When** открывается страница, **Then** показаны SHA, версии
   скилла, рубрики, схемы, модель и время оценки.
2. **Given** SHA, **When** пользователь кликает по нему, **Then** открывается коммит в
   репозитории.
3. **Given** оценка с флагом `needs_review` или предупреждениями (`warnings`), **When**
   открывается страница, **Then** они показаны с пояснением, что это значит.
4. **Given** оценка с переопределением жюри, **When** открывается страница, **Then** видны
   исходная оценка модели, оценка жюри и комментарий.

---

### Edge Cases

- Команда оценена только по одной области → вторая область показана как «нет данных», графики по
  ней не рисуются.
- Оценка в процессе → страница показывает прогресс вместо неполных данных.
- Оценка упала → показана причина и предложение перезапустить (для жюри).
- Критерий без находок → невозможно по контракту 001; при получении таких данных показывается
  ошибка данных, а не пустой блок.
- Очень длинный сниппет → сворачивается с возможностью раскрыть, ссылка на полный фрагмент
  сохраняется.
- Файл сниппета на языке без подсветки → показывается как обычный текст с номерами строк.
- Оценка сделана по старой версии рубрики → показываются якоря именно той версии, с пометкой о
  версии.

## Requirements *(mandatory)*

### Functional Requirements

#### Обзор и графики

- **FR-001**: Страница MUST отображать radar-график баллов по критериям отдельно для backend и
  frontend.
- **FR-002**: На radar-график MUST накладываться медиана соответствующего критерия по всем
  оценённым командам.
- **FR-003**: Страница MUST отображать bar-график «команда против среднего» по каждому критерию.
- **FR-004**: При недостатке данных для медианы/среднего страница MUST это явно сообщать, а
  MUST NOT рисовать вводящие в заблуждение линии.
- **FR-005**: Страница MUST отображать итоговый балл команды и баллы по областям, полученные из
  API без пересчёта на клиенте.
- **FR-006**: Графики MUST быть читаемы в обеих темах оформления и иметь текстовую альтернативу
  (значения доступны не только в виде графика).

#### Drill-down

- **FR-007**: Страница MUST позволять раскрыть любой критерий и показать балл, `summary`,
  `rationale` и уровень `confidence`.
- **FR-008**: Раскрытый критерий MUST показывать описание критерия и якоря уровней из рубрики той
  версии, которой выставлена оценка.
- **FR-009**: Страница MUST показывать находки критерия с типом (`strength`/`issue`) и
  серьёзностью.
- **FR-010**: Сниппеты кода MUST отображаться с подсветкой синтаксиса, номерами строк и
  выделением указанного диапазона.
- **FR-011**: Каждая находка MUST иметь постоянную ссылку на участок кода в репозитории на
  зафиксированном SHA.
- **FR-012**: Находки с непроверенными ссылками MUST быть явно помечены.
- **FR-013**: Страница MUST NOT показывать код, пришедший из ответа модели, как содержимое файла.
- **FR-014**: Для находок типа `issue` страница MUST показывать рекомендацию по улучшению.

#### Находки и метаданные

- **FR-015**: Страница MUST показывать распределение находок по типу и серьёзности.
- **FR-016**: Страница MUST позволять фильтровать находки по типу и серьёзности.
- **FR-017**: Страница MUST показывать метаданные: SHA, версии скилла, рубрики и схемы, модель,
  время оценки.
- **FR-018**: Страница MUST показывать предупреждения (`warnings`) и флаг `needs_review` с
  человекочитаемым пояснением.
- **FR-019**: При наличии переопределения жюри страница MUST показывать обе оценки и комментарий
  жюри.
- **FR-020**: Страница MUST корректно отображать состояния: загрузка, оценка выполняется, оценка
  не удалась, нет данных.
- **FR-021**: Ссылка на конкретный раскрытый критерий MUST быть адресуемой, чтобы её можно было
  переслать.
- **FR-022**: Страница MUST отображать график динамики итога и баллов по областям по истории
  оценок команды (время и SHA каждой точки).
- **FR-023**: При наличии менее двух точек истории страница MUST явно сообщать о недостатке данных
  вместо отрисовки графика.
- **FR-024**: Страница MUST позволять выбрать точку истории и показать данные именно той оценки, а
  не только последней.
- **FR-025**: Точки истории с недоступным коммитом MUST оставаться в графике с соответствующей
  пометкой.

### Key Entities

- **Профиль команды (TeamProfile)**: баллы по критериям обеих областей, итоги, сравнение с
  медианой и средним.
- **Блок критерия (CriterionPanel)**: балл, вывод, обоснование, `confidence`, описание и якоря,
  находки.
- **Отображаемая находка (FindingView)**: тип, серьёзность, заголовок, объяснение, рекомендация,
  сниппет, ссылка, признак валидности ссылки.
- **Метаданные оценки (EvaluationMeta)**: SHA, версии, модель, время, предупреждения, флаги.
- **Точка истории (HistoryPoint)**: время, SHA, итог, баллы по областям, доступность коммита.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Участник за одну минуту определяет два самых слабых критерия своей команды и
  находит конкретные места в коде, которые это подтверждают.
- **SC-002**: 100% находок на странице сопровождаются сниппетом из репозитория либо явной
  пометкой о непроверенной ссылке.
- **SC-003**: Для 100% критериев доступен блок «как оценивается» с якорями уровней.
- **SC-004**: Страница полностью работает на фикстурах без запущенного runner.
- **SC-005**: Спор команды с оценкой разрешается по данным страницы без обращения к разработчикам
  платформы.
- **SC-006**: Страница остаётся пригодной к использованию на экране шириной от 360 px.

## Assumptions

- Подсветка синтаксиса выполняется на клиенте или на этапе сборки, без обращения к внешним
  сервисам.
- Медианы и средние приходят из API (эндпойнт статистики), а не считаются на клиенте; история
  оценок — из эндпойнта истории (следствие Q2).
- Пользователи страницы — участники и жюри; редактирование оценок относится к фиче 007.
- Постоянные ссылки строятся ingestion; страница их только отображает.
- Графики строятся по одной рубрике за раз — критерии backend и frontend не смешиваются.

## Dependencies

- **001-evaluation-contract**: структура отчёта, рубрики, фикстуры (блокирующая).
- **004-api**: данные команды, рубрики и статистика в рабочем режиме.
- **003-runner-ingestion**: сниппеты и постоянные ссылки в рабочем режиме.
