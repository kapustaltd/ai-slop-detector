# Feature Specification: Контракт оценки (JSON Schema + рубрики)

**Feature Branch**: `001-evaluation-contract`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "Контракт оценки — JSON-схема отчёта и версионированные рубрики backend/frontend с якорями по уровням. Критический путь: блокирует все остальные фичи."

## Overview

Контракт оценки — единственная точка связи между скиллами-ревьюерами, пайплайном ingestion, API и
UI. Он состоит из двух версионированных артефактов:

1. **JSON Schema отчёта** — структура результата оценки одной области (backend или frontend) одной
   команды на одном коммите.
2. **Рубрики** (`backend.v1.yaml`, `frontend.v1.yaml`) — перечень критериев с весами, описаниями и
   **якорями по уровням** (что означает 2, 5, 8 и 10 баллов).

Пока контракт не зафиксирован, ни одна другая фича не может быть реализована безопасно. Как только
он зафиксирован, UI и API работают на фикстурах, а скиллы дорабатываются независимо.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Фиксация структуры отчёта (Priority: P1)

Команда платформы фиксирует структуру отчёта об оценке так, чтобы автор скилла, автор ingestion и
автор UI могли работать параллельно, не согласовывая поля между собой. Структура лежит в
репозитории, версионируется и проверяется автоматически.

**Why this priority**: без зафиксированной структуры параллельная разработка невозможна; это
критический путь всего проекта.

**Independent Test**: можно полностью проверить, взяв набор фикстур и прогнав валидацию: валидные
отчёты проходят, невалидные отвергаются с понятным сообщением об ошибке.

**Acceptance Scenarios**:

1. **Given** валидный отчёт по backend-области, **When** он валидируется по схеме, **Then**
   валидация проходит успешно.
2. **Given** отчёт без поля `meta.commit_sha`, **When** он валидируется по схеме, **Then**
   валидация падает с указанием отсутствующего поля.
3. **Given** отчёт, где `score` больше `max`, **When** он валидируется, **Then** валидация падает.
4. **Given** отчёт, где `findings` пуст у критерия, **When** он валидируется, **Then** валидация
   падает (принцип прозрачности: балл без ссылки на код недопустим).
5. **Given** отчёт, где `line_end` меньше `line_start`, **When** он валидируется, **Then**
   валидация падает.

---

### User Story 2 - Рубрика с якорями по уровням (Priority: P1)

Жюри и автор скилла фиксируют перечень критериев для backend и frontend: у каждого критерия есть
вес, описание и якоря — словесные описания того, что означает 2, 5, 8 и 10 баллов. Якоря
используются и моделью при оценке, и UI в блоке «как оценивается».

**Why this priority**: без якорей оценки плавают между командами и прогонами; рубрика — основа
справедливости и воспроизводимости.

**Independent Test**: можно проверить независимо — загрузить рубрику, убедиться, что сумма весов
даёт 100%, у каждого критерия есть все четыре якоря и уникальный `id`.

**Acceptance Scenarios**:

1. **Given** рубрика `backend.v1`, **When** она валидируется, **Then** сумма весов критериев равна
   1.0 (100%) с точностью до 0.001.
2. **Given** рубрика с двумя критериями с одинаковым `id`, **When** она валидируется, **Then**
   валидация падает.
3. **Given** рубрика, где у критерия отсутствует якорь уровня 8, **When** она валидируется,
   **Then** валидация падает.
4. **Given** отчёт со ссылкой на `rubric_version: backend.v1`, **When** проверяется соответствие
   отчёта рубрике, **Then** набор `criteria[].id` в отчёте совпадает с набором критериев рубрики.

---

### User Story 3 - Типы для разработчиков платформы (Priority: P2)

Разработчик backend-части и разработчик UI получают типы, сгенерированные из схемы, и
подтягивают их как зависимость. При изменении схемы типы пересобираются, и несоответствие ломает
сборку, а не всплывает в рантайме на демо.

**Why this priority**: снижает стоимость параллельной работы и предотвращает тихое расхождение
контракта с кодом; нужен сразу после того, как схема зафиксирована.

**Independent Test**: запустить генерацию типов и убедиться, что сгенерированные артефакты
совпадают с закоммиченными (проверка «нет незакоммиченного дрейфа»).

**Acceptance Scenarios**:

1. **Given** схема в репозитории, **When** запускается генерация типов, **Then** типы для backend
   и frontend создаются без ошибок.
2. **Given** схема изменена, а типы не перегенерированы, **When** запускается проверка в CI,
   **Then** проверка падает с указанием на расхождение.

---

### User Story 4 - Фикстуры для параллельной разработки (Priority: P2)

Разработчик UI и API начинает работу до появления реальных отчётов: берёт готовые фикстуры
(хороший проект, средний, проект со слабыми местами) и строит на них рейтинг, графики и
drill-down.

**Why this priority**: обеспечивает параллельность этапов 2 и 3 из плана; без фикстур UI ждёт
скиллы.

**Independent Test**: собрать UI/API на фикстурах без единого обращения к модели.

**Acceptance Scenarios**:

1. **Given** набор валидных фикстур, **When** он валидируется по схеме, **Then** все фикстуры
   проходят валидацию.
2. **Given** набор невалидных фикстур, **When** он валидируется, **Then** каждая падает по
   ожидаемой причине, зафиксированной рядом с фикстурой.

---

### Edge Cases

- Отчёт содержит критерий, которого нет в рубрике указанной версии → отчёт считается невалидным.
- Отчёт не содержит части критериев рубрики → отчёт считается невалидным (оценка неполная).
- `findings` ссылается на файл, которого нет в репозитории → схема пропускает (существование файла
  проверяется на этапе ingestion, фича 003), но поле пути обязано быть непустым и относительным.
- `warnings` содержит значение вне перечисленного набора → валидация падает; набор расширяется
  только через новую версию схемы.
- Поле `suggestion` заполнено у находки типа `strength` → допустимо, но не обязательно; у `issue`
  обязательно.
- Слишком длинные текстовые поля (rationale на десятки килобайт) → ограничиваются максимальной
  длиной, чтобы UI и хранилище оставались предсказуемыми.
- Рубрика с весом 0 у критерия → допустима (критерий информационный, не влияет на балл), но должна
  быть явно помечена.

## Requirements *(mandatory)*

### Functional Requirements

#### Схема отчёта

- **FR-001**: Репозиторий MUST содержать JSON Schema отчёта об оценке в виде файла, доступного
  всем компонентам платформы.
- **FR-002**: Схема MUST быть версионирована, а версия MUST быть явно указана внутри самого
  отчёта.
- **FR-003**: Схема MUST требовать блок `meta` с полями: `team_id`, `area` (`backend` |
  `frontend`), `repo`, `commit_sha`, `skill_version`, `rubric_version`, `model`, `evaluated_at`.
- **FR-004**: Схема MUST требовать непустой массив `criteria`, где каждый элемент содержит `id`,
  `score`, `max`, `confidence` (`high` | `medium` | `low`), `summary`, `rationale` и непустой
  массив `findings`.
- **FR-005**: Схема MUST требовать, чтобы каждая находка содержала `kind` (`strength` | `issue`),
  `severity` (`info` | `minor` | `major` | `critical`), `file`, `line_start`, `line_end`, `title`,
  `explanation`; поле `suggestion` MUST быть обязательным для находок типа `issue`.
- **FR-006**: Схема MUST запрещать дополнительные поля, не описанные в ней, на всех уровнях
  вложенности.
- **FR-007**: Схема MUST ограничивать `score` диапазоном от 0 до `max` включительно и требовать
  `line_end >= line_start >= 1`.
- **FR-008**: Схема MUST содержать поля `overall_comment` и `warnings`, где `warnings` — массив
  значений из фиксированного перечня (включая `suspected_prompt_injection`, `repo_too_large`).
- **FR-009**: Схема MUST NOT содержать полей с итоговыми или агрегированными баллами: итог по
  области и по команде считается кодом (принцип VI конституции).
- **FR-010**: Схема MUST ограничивать максимальную длину текстовых полей и максимальное число
  находок на критерий.
- **FR-011**: `commit_sha` MUST быть полным 40-символьным hex-идентификатором; сокращённые формы
  отвергаются (воспроизводимость).
- **FR-012**: `file` в находке MUST быть относительным путём внутри репозитория команды; абсолютные
  пути и выход за пределы репозитория (`..`) отвергаются.

#### Рубрики

- **FR-013**: Репозиторий MUST содержать рубрики `rubrics/backend.v1.yaml` и
  `rubrics/frontend.v1.yaml`.
- **FR-014**: Каждый критерий рубрики MUST содержать `id`, человекочитаемое название, вес,
  описание и якоря для уровней 2, 5, 8 и 10.
- **FR-015**: Сумма весов критериев внутри рубрики MUST равняться 1.0 (с допуском 0.001).
- **FR-016**: `id` критериев внутри рубрики MUST быть уникальны и стабильны между версиями (смена
  смысла критерия требует нового `id`).
- **FR-017**: Рубрика `backend.v1` MUST покрывать: архитектуру и структуру, читаемость, обработку
  ошибок, дизайн API, работу с данными, безопасность, тесты, конфигурацию и инфраструктуру.
- **FR-018**: Рубрика `frontend.v1` MUST покрывать: компонентную структуру, управление состоянием,
  типизацию, производительность, доступность, консистентность стилей, тесты.
- **FR-019**: Рубрики MUST валидироваться собственной схемой, а не только глазами человека.
- **FR-020**: Формат рубрики MUST позволять указывать вес 0 для информационных критериев, не
  влияющих на итоговый балл.

#### Согласованность и версионирование

- **FR-021**: Платформа MUST уметь проверять согласованность отчёта и рубрики: набор `criteria[].id`
  в отчёте совпадает с набором критериев рубрики, указанной в `meta.rubric_version`, а `max`
  совпадает с максимумом шкалы рубрики.
- **FR-022**: Изменение схемы MUST сопровождаться повышением её версии; несовместимое изменение
  MUST означать новую major-версию и переоценку всех команд.
- **FR-023**: Репозиторий MUST содержать не менее 3 валидных и не менее 3 невалидных фикстур, у
  каждой невалидной MUST быть зафиксирована ожидаемая причина отказа.
- **FR-024**: Типы для backend и frontend MUST генерироваться из схемы автоматически, а проверка
  актуальности сгенерированных типов MUST выполняться в CI.
- **FR-025**: Шкала оценки (максимальный балл критерия) MUST быть единой для всех критериев всех
  рубрик текущей мажорной версии контракта.

### Key Entities

- **Отчёт об оценке (EvaluationReport)**: результат оценки одной области одной команды на одном
  коммите. Содержит метаданные прогона, оценки по критериям, общий комментарий и предупреждения.
- **Метаданные (ReportMeta)**: координаты воспроизводимости — команда, область, репозиторий, SHA,
  версия скилла, версия рубрики, модель, время оценки, версия схемы.
- **Оценка критерия (CriterionScore)**: балл по одному критерию с уровнем уверенности, кратким
  выводом, развёрнутым обоснованием и набором находок.
- **Находка (Finding)**: конкретное место в коде — сильная сторона или проблема — с путём,
  диапазоном строк, заголовком, объяснением и (для проблем) рекомендацией.
- **Рубрика (Rubric)**: версионированный набор критериев для одной области с весами и якорями.
- **Критерий рубрики (RubricCriterion)**: `id`, название, вес, описание, якоря уровней 2/5/8/10.
- **Фикстура (Fixture)**: эталонный отчёт (валидный или невалидный) для тестов и для разработки UI
  без модели.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% валидных фикстур проходят валидацию, 100% невалидных отвергаются с ожидаемой
  причиной.
- **SC-002**: Разработчик UI может собрать страницу команды и рейтинг, не обращаясь ни к модели,
  ни к API — только на фикстурах.
- **SC-003**: Сумма весов в каждой рубрике равна 100%, у 100% критериев присутствуют все четыре
  якоря — проверяется автоматически.
- **SC-004**: Любое изменение схемы, не сопровождённое перегенерацией типов, падает в CI.
- **SC-005**: Человек, не участвовавший в разработке, по рубрике и схеме может объяснить, почему у
  критерия стоит конкретный балл, не заглядывая в код платформы.
- **SC-006**: Валидация одного отчёта занимает менее 100 мс, что позволяет валидировать поток
  отчётов в ingestion без заметной задержки.

## Assumptions

- Схема описывает отчёт по **одной области** (backend или frontend) — команда с двумя областями
  получает два отчёта; агрегация между областями относится к фиче 003.
- Максимальный балл критерия единый и равен 10; якоря даны для уровней 2/5/8/10, промежуточные
  баллы допускаются и интерпретируются между соседними якорями.
- Веса задаются долями от 1.0, а не процентами, чтобы исключить ошибки округления.
- Язык текстовых полей отчёта (`summary`, `rationale`, `explanation`) — русский; схема язык не
  валидирует.
- Сниппеты кода в схеме отсутствуют: их добавляет ingestion, вырезая из репозитория по SHA
  (принцип «код из репозитория, а не из ответа модели»).
- Рубрики хранятся в YAML в каталоге `rubrics/` в корне репозитория платформы.
- Версия схемы указывается внутри отчёта, чтобы старые сохранённые отчёты оставались
  интерпретируемыми после обновления контракта.

## Dependencies

- Нет. Это первая фича, она блокирует 002–007.
