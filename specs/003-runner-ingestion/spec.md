# Feature Specification: Runner и ingestion

**Feature Branch**: `003-runner-ingestion`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "Запуск оценки: клон репозитория на SHA, прогон скилла в изоляции, валидация, обогащение сниппетами, K прогонов с медианой, агрегация баллов кодом, статусы и очередь."

## Overview

Runner превращает «репозиторий команды» в «сохранённые данные оценки». Он отвечает за всё, что
находится между репозиторием и API: подготовку рабочей копии, изолированный прогон скилла,
валидацию вывода, проверку ссылок на код, вырезку сниппетов, устойчивость к разбросу оценок и
детерминированный расчёт итоговых баллов.

Ключевое разделение ответственности: **модель ставит баллы по критериям, runner считает всё
остальное**.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Оценка одной команды от репозитория до сохранённых данных (Priority: P1)

Оператор ставит команду в очередь на оценку. Система клонирует репозиторий на зафиксированный
SHA, прогоняет скиллы по областям, валидирует результат, проверяет ссылки на код, вырезает
сниппеты, считает итоговые баллы и сохраняет всё вместе с сырым ответом модели.

**Why this priority**: это основной поток данных платформы; без него UI нечего показывать.

**Independent Test**: поставить в очередь один репозиторий и убедиться, что в хранилище появились
валидный отчёт, сниппеты, вычисленные баллы и метаданные прогона.

**Acceptance Scenarios**:

1. **Given** команда с указанным репозиторием и SHA, **When** запускается оценка, **Then** статус
   проходит путь `pending → running → done`, а в хранилище лежат отчёт и вычисленные баллы.
2. **Given** завершённая оценка, **When** запрашиваются её данные, **Then** доступны и сырой ответ
   модели, и обогащённая версия.
3. **Given** недоступный репозиторий или несуществующий SHA, **When** запускается оценка, **Then**
   статус становится `failed` с понятной причиной, и это видно оператору.

---

### User Story 2 - Валидация и повтор при невалидном выводе (Priority: P1)

Модель иногда возвращает JSON, не соответствующий схеме. Система не роняет прогон: она
возвращает модели текст ошибки валидации и просит исправить, и только после нескольких неудачных
попыток помечает прогон как `failed`.

**Why this priority**: без этого доля неудачных прогонов делает платформу неработоспособной.

**Independent Test**: подать заведомо невалидный вывод и проверить, что система делает повтор с
текстом ошибки, а затем корректно завершает прогон.

**Acceptance Scenarios**:

1. **Given** вывод, невалидный по схеме, **When** он поступает в валидатор, **Then** выполняется
   повторный запрос с текстом ошибки (не более двух повторов).
2. **Given** три подряд невалидных вывода, **When** попытки исчерпаны, **Then** прогон получает
   статус `failed`, а все сырые ответы сохраняются для разбора.
3. **Given** валидный по схеме, но не соответствующий рубрике вывод (лишний или пропущенный
   критерий), **When** он проверяется, **Then** он отвергается так же, как невалидный по схеме.

---

### User Story 3 - Проверка ссылок на код и вырезка сниппетов (Priority: P1)

Модель может сослаться на несуществующий файл или на строки за пределами файла. Система проверяет
каждую ссылку на зафиксированном SHA, вырезает сниппет из репозитория, строит постоянную ссылку и
помечает невалидные ссылки, вместо того чтобы молча их выбрасывать.

**Why this priority**: галлюцинированная ссылка на код разрушает доверие к платформе сильнее, чем
неточный балл; это принцип прозрачности.

**Independent Test**: подать отчёт со смесью валидных и невалидных ссылок и проверить результат
обогащения по каждой.

**Acceptance Scenarios**:

1. **Given** находка со ссылкой на существующий файл и корректный диапазон строк, **When**
   выполняется обогащение, **Then** к находке добавляются сниппет кода и постоянная ссылка вида
   `blob/<sha>/path#L42-L58`.
2. **Given** находка со ссылкой на несуществующий файл, **When** выполняется обогащение, **Then**
   находка помечается как непроверенная, сохраняется и остаётся видимой жюри.
3. **Given** находка с диапазоном строк, выходящим за пределы файла, **When** выполняется
   обогащение, **Then** диапазон помечается как некорректный, сниппет не подменяется выдуманным
   содержимым.
4. **Given** слишком большой диапазон строк, **When** вырезается сниппет, **Then** он
   ограничивается разумным размером с сохранением ссылки на полный диапазон.

---

### User Story 4 - Устойчивость оценок: K прогонов и медиана (Priority: P2)

Чтобы оценка не зависела от случайности одного прогона, система выполняет несколько прогонов на
область и берёт медиану по каждому критерию. Если разброс слишком велик, команда помечается как
требующая внимания жюри.

**Why this priority**: снижает главный риск проекта — нестабильность оценок; но требует уже
работающего одиночного прогона.

**Independent Test**: подать набор из K заранее заготовленных отчётов и проверить вычисленную
медиану и флаг разброса.

**Acceptance Scenarios**:

1. **Given** K прогонов по области, **When** вычисляется итог, **Then** балл по каждому критерию
   равен медиане баллов этого критерия по прогонам.
2. **Given** разброс по критерию больше порога, **When** вычисляется итог, **Then** оценка
   помечается статусом `needs_review`.
3. **Given** часть прогонов завершилась ошибкой, **When** успешных прогонов меньше необходимого
   минимума, **Then** оценка получает статус `needs_review` или `failed` в зависимости от того,
   есть ли хотя бы один успешный прогон.
4. **Given** вычисленная медиана, **When** запрашиваются данные оценки, **Then** видно, из каких
   именно прогонов она получена.

---

### User Story 5 - Детерминированный расчёт итоговых баллов (Priority: P1)

Итог по области — взвешенная сумма баллов критериев по весам рубрики. Итог команды — агрегация
областей. Всё считает код, результат пересчитывается из сохранённых данных в любой момент.

**Why this priority**: рейтинг и все сравнения строятся на этих числах; это принцип VI
конституции.

**Independent Test**: подать отчёт с известными баллами и рубрику с известными весами и сверить
вычисленный итог с рассчитанным вручную.

**Acceptance Scenarios**:

1. **Given** отчёт с баллами и рубрика с весами, **When** вычисляется итог по области, **Then** он
   равен взвешенной сумме с точностью до заданного округления.
2. **Given** оценки по обеим областям, **When** вычисляется итог команды, **Then** применяется
   зафиксированная формула агрегации.
3. **Given** команда, у которой оценена только одна область, **When** вычисляется итог, **Then**
   применяется правило для неполных данных, зафиксированное в спецификации.
4. **Given** изменённые веса рубрики (новая версия), **When** выполняется переоценка, **Then**
   итоги пересчитываются для всех команд.

---

### User Story 6 - Очередь, стоимость и наблюдаемость (Priority: P2)

Оператор видит, сколько прогонов в очереди, сколько времени и денег потрачено, и может
ограничить параллельность, чтобы не упереться в лимиты.

**Why this priority**: без контроля стоимости и параллельности прогон на реальном хакатоне
непредсказуем; но это не блокирует основной поток.

**Independent Test**: поставить в очередь больше задач, чем лимит параллельности, и проверить,
что одновременно выполняется не больше разрешённого числа.

**Acceptance Scenarios**:

1. **Given** лимит параллельности N, **When** в очереди больше N задач, **Then** одновременно
   выполняется не более N.
2. **Given** завершённый прогон, **When** смотрят его метаданные, **Then** доступны
   длительность и стоимость (токены/деньги).
3. **Given** упавший прогон, **When** оператор запускает его повтор, **Then** предыдущие данные
   сохраняются, а не затираются.

---

### Edge Cases

- Репозиторий огромный (сотни мегабайт, монорепа) → применяются лимиты, ставится флаг
  `repo_too_large`, анализ ограничивается релевантными путями.
- В репозитории есть только одна из областей → вторая область не оценивается, итог считается по
  правилу неполных данных.
- Репозиторий содержит секреты или вредоносные скрипты → прогон изолирован, ничего не выполняется,
  секреты не логируются.
- Скилл вернул валидный JSON, но с нулевым числом находок по критерию → отвергается (нарушение
  контракта 001).
- Два одновременных запроса на оценку одной команды → второй не создаёт дубликат, а присоединяется
  к текущему прогону или отклоняется.
- SHA изменился между постановкой в очередь и запуском → оценивается именно тот SHA, который
  зафиксирован в задаче.
- Модель недоступна или отвечает ошибкой лимитов → прогон повторяется с задержкой, после исчерпания
  попыток статус `failed`.

## Requirements *(mandatory)*

### Functional Requirements

#### Подготовка и изоляция

- **FR-001**: Система MUST клонировать репозиторий команды и переключаться на явно
  зафиксированный `commit_sha`.
- **FR-002**: Прогон MUST выполняться в изолированном окружении без доступа к секретам платформы и
  без лишнего сетевого доступа.
- **FR-003**: Система MUST NOT выполнять код из репозитория команды (сборку, скрипты, тесты).
- **FR-004**: Система MUST применять лимиты на размер репозитория и число анализируемых файлов, а
  превышение MUST отражать в `warnings`.
- **FR-005**: Система MUST определять пути областей (backend/frontend) либо по указанию команды при
  сабмите, либо по признакам структуры репозитория.

#### Прогон и валидация

- **FR-006**: Система MUST запускать скиллы оценки в неинтерактивном режиме и собирать их JSON-вывод.
- **FR-007**: Система MUST валидировать вывод по схеме контракта 001 и по рубрике указанной версии.
- **FR-008**: При невалидном выводе система MUST выполнить повтор с текстом ошибки валидации, не
  более двух повторов, после чего присвоить статус `failed`.
- **FR-009**: Система MUST сохранять сырой ответ модели всегда, включая ответы неудачных попыток.
- **FR-010**: Система MUST фиксировать в метаданных прогона версию скилла, версию рубрики, модель,
  SHA и время.

#### Обогащение

- **FR-011**: Система MUST проверять существование каждого файла из находок на указанном SHA.
- **FR-012**: Система MUST проверять, что диапазон строк находки существует в файле.
- **FR-013**: Система MUST вырезать сниппет кода из репозитория на указанном SHA; содержимое кода
  из ответа модели MUST NOT использоваться как содержимое файла.
- **FR-014**: Система MUST генерировать постоянную ссылку на участок кода вида
  `blob/<sha>/<path>#L<start>-L<end>`.
- **FR-015**: Невалидные ссылки MUST помечаться и сохраняться, а MUST NOT молча отбрасываться.
- **FR-016**: Система MUST ограничивать размер сохраняемого сниппета.

#### Устойчивость и расчёты

- **FR-017**: Система MUST выполнять K прогонов на область (K настраивается, по умолчанию 3) и
  брать медиану балла по каждому критерию.
- **FR-018**: Система MUST помечать оценку флагом `needs_review`, если разброс баллов по критерию
  между прогонами превышает порог.
- **FR-019**: Итог по области MUST вычисляться кодом как взвешенная сумма баллов критериев по
  весам рубрики.
- **FR-020**: Итог команды MUST вычисляться кодом из итогов по областям по зафиксированной формуле
  [NEEDS CLARIFICATION: формула агрегации frontend + backend — поровну, по весам областей, или
  зависит от типа проекта?].
- **FR-021**: Система MUST задавать правило расчёта для команд с одной оценённой областью.
- **FR-022**: Все вычисленные величины MUST быть пересчитываемы из сохранённых данных без нового
  обращения к модели.

#### Статусы, очередь, наблюдаемость

- **FR-023**: Оценка MUST иметь статус из набора `pending`, `running`, `done`, `failed`,
  `needs_review`.
- **FR-024**: Система MUST ограничивать число одновременных прогонов настраиваемым лимитом.
- **FR-025**: Система MUST логировать длительность и стоимость каждого прогона.
- **FR-026**: Повторная оценка MUST NOT удалять предыдущую; история прогонов MUST сохраняться.
- **FR-027**: Система MUST поддерживать режим запуска оценки [NEEDS CLARIFICATION: однократный
  прогон после дедлайна или периодические прогоны по ходу хакатона с историей по SHA и графиком
  динамики?].
- **FR-028**: Источник репозиториев команд MUST быть определён [NEEDS CLARIFICATION: команды сами
  сабмитят ссылку на репозиторий и ветку, или организаторы забирают репозитории сами?].

### Key Entities

- **Задача оценки (EvaluationJob)**: команда, область, репозиторий, SHA, статус, время постановки
  и завершения, лимиты.
- **Прогон (Run)**: один вызов скилла в рамках задачи; хранит сырой ответ, результат валидации,
  длительность и стоимость.
- **Оценка области (AreaEvaluation)**: итог по области — медианные баллы по критериям, взвешенный
  итог, флаги, ссылка на прогоны.
- **Оценка команды (TeamEvaluation)**: агрегированный итог по командам, статус, метки
  `needs_review`.
- **Обогащённая находка (EnrichedFinding)**: находка модели плюс сниппет, постоянная ссылка и
  признак валидности ссылки.
- **Запись стоимости (RunCost)**: токены, деньги и время прогона.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 95% задач оценки доходят до статуса `done` без ручного вмешательства.
- **SC-002**: 100% находок, попавших в UI, содержат сниппет, вырезанный из репозитория, либо явную
  пометку о невалидной ссылке.
- **SC-003**: Итоговые баллы пересчитываются из сохранённых данных и совпадают с ранее
  сохранёнными при неизменной рубрике (детерминированность).
- **SC-004**: Ни один прогон не имеет доступа к секретам платформы — проверяется тестом
  изоляции.
- **SC-005**: Оператор в любой момент видит текущее распределение задач по статусам.
- **SC-006**: Суммарная стоимость и время прогона по всем командам известны и доступны отчётом.
- **SC-007**: Оценка одной команды (обе области, K прогонов) укладывается в заранее оговорённый
  бюджет времени, достаточный для прогона всех команд до подведения итогов.

## Assumptions

- Скиллы из фичи 002 доступны и корректны; ingestion не правит их поведение, только валидирует
  вывод.
- K по умолчанию равен 3; значение настраивается без изменения кода.
- Порог разброса для `needs_review` задаётся конфигурацией и калибруется на golden set.
- Постоянные ссылки строятся по шаблону хостинга репозитория (GitHub-совместимый формат).
- Хранилище — PostgreSQL (решение владельца продукта, Q1); масштаб — десятки команд, не тысячи.
- Изоляция прогона достигается контейнером без смонтированных секретов.

## Dependencies

- **001-evaluation-contract**: схема и рубрики (блокирующая).
- **002-review-skills**: скиллы оценки (для реального прогона; валидация и обогащение
  разрабатываются на фикстурах).
