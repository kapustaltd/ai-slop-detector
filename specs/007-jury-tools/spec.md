# Feature Specification: Инструменты жюри

**Feature Branch**: `007-jury-tools`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "Инструменты жюри: переопределение оценки критерия с обязательным комментарием (обе версии видны), перезапуск оценки, пометка «проверено жюри». Реализуется, если останется время."

## Overview

Платформа помогает жюри, но не заменяет его. Инструменты жюри дают возможность исправить оценку,
когда модель ошиблась, не теряя исходных данных: и оценка модели, и решение жюри видны рядом, с
комментарием, объясняющим правку.

Фича низкоприоритетная: реализуется после того, как основной поток работает end-to-end.

## Clarifications

### Session 2026-09-21

- Q: К чему привязаны пометка «проверено жюри» и переопределения оценок? → A: к конкретному
  прогону. Штатно оценка выполняется один раз после дедлайна, поэтому сброс происходит только при
  перезапуске оценки жюри, а не по расписанию.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Переопределение оценки критерия (Priority: P1 внутри фичи)

Член жюри видит, что модель занизила балл по критерию, ставит свою оценку и обязательно
объясняет, почему. В интерфейсе после этого видны обе оценки.

**Why this priority**: это основная функция фичи — принцип V конституции «последнее слово за
жюри».

**Independent Test**: переопределить оценку на фикстурной команде и убедиться, что исходная
оценка сохранилась, итог пересчитан, а обе версии видны.

**Acceptance Scenarios**:

1. **Given** оценённый критерий, **When** жюри вводит новый балл и комментарий, **Then**
   переопределение сохраняется, исходная оценка модели остаётся доступна.
2. **Given** попытка переопределить балл без комментария, **When** форма отправляется, **Then**
   операция отклоняется с требованием комментария.
3. **Given** переопределённый критерий, **When** пересчитывается итог по области и команде,
   **Then** в расчёт идёт оценка жюри, и это явно помечено в интерфейсе.
4. **Given** переопределение, **When** оно отменяется, **Then** восстанавливается оценка модели, а
   факт отмены остаётся в истории.
5. **Given** балл вне допустимой шкалы, **When** он вводится, **Then** операция отклоняется.

---

### User Story 2 - Перезапуск оценки (Priority: P2)

Жюри перезапускает оценку команды: например, команда прислала правильный SHA или прогон упал.

**Why this priority**: чинит самые частые операционные проблемы; частично покрывается эндпойнтом
из фичи 004.

**Independent Test**: запустить перезапуск и проверить появление новой задачи и сохранность
старых данных.

**Acceptance Scenarios**:

1. **Given** команда с завершённой или упавшей оценкой, **When** жюри запускает перезапуск,
   **Then** создаётся новая задача, старая оценка сохраняется в истории.
2. **Given** идущий прогон, **When** запрашивается ещё один перезапуск, **Then** дубликат не
   создаётся.
3. **Given** завершённый перезапуск, **When** у команды были переопределения жюри, **Then**
   система явно показывает, что переопределения относятся к предыдущему прогону, и требует
   решения жюри.

---

### User Story 3 - Пометка «проверено жюри» (Priority: P2)

Жюри отмечает команды, которые уже просмотрены вручную, чтобы не проверять их дважды и чтобы
снять флаг `needs_review`.

**Why this priority**: превращает список «требуют внимания» в рабочий процесс с понятным
завершением.

**Independent Test**: пометить команду проверенной и убедиться, что она уходит из фильтра
«требуют ревью».

**Acceptance Scenarios**:

1. **Given** команда с флагом `needs_review`, **When** жюри помечает её проверенной, **Then** в
   рейтинге отображается пометка «проверено жюри».
2. **Given** помеченная команда, **When** применяется фильтр «требуют ревью», **Then** она в него
   не попадает.
3. **Given** новый прогон оценки, **When** он завершается, **Then** пометка «проверено» сбрасывается
   для нового прогона.
4. **Given** пометка, **When** смотрят её детали, **Then** видно, кто и когда пометил.

---

### Edge Cases

- Два члена жюри одновременно переопределяют один критерий → сохраняется последнее решение, а
  конфликт виден в истории; предыдущее решение не теряется.
- Переопределение критерия у команды, оценка которой ещё выполняется → операция откладывается
  или отклоняется с понятным объяснением.
- Переопределены все критерии области → итог считается полностью по оценкам жюри, и это видно.
- Жюри переопределяет оценку, а затем меняется версия рубрики → переопределения привязаны к
  версии рубрики и не переносятся автоматически.
- Действие жюри без авторизации → отклоняется.
- Жюри перезапустило оценку вскоре после переопределения → переопределение остаётся привязанным к
  прежнему прогону, новая оценка приходит без него, и это явно видно жюри.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST позволять авторизованному члену жюри переопределить балл по любому
  критерию любой команды.
- **FR-002**: Переопределение MUST требовать обязательного текстового комментария.
- **FR-003**: Система MUST сохранять исходную оценку модели неизменной; переопределение MUST
  храниться отдельно.
- **FR-004**: UI MUST показывать обе оценки — модели и жюри — вместе с комментарием.
- **FR-005**: Итоговые баллы MUST пересчитываться кодом с учётом переопределений, по тем же
  правилам и весам.
- **FR-006**: Система MUST позволять отменить переопределение с сохранением факта в истории.
- **FR-007**: Система MUST фиксировать автора и время каждого действия жюри.
- **FR-008**: Система MUST позволять перезапустить оценку команды без потери предыдущих данных.
- **FR-009**: Система MUST позволять пометить команду как «проверено жюри»; пометка MUST быть
  привязана к конкретному прогону и MUST сниматься, когда появляется оценка на новом `commit_sha`.
- **FR-010**: Все действия жюри MUST требовать авторизации.
- **FR-011**: Переопределения MUST быть привязаны к конкретному прогону и версии рубрики.
- **FR-012**: Система MUST вести журнал действий жюри, доступный для просмотра.
- **FR-013**: Балл, вводимый жюри, MUST проверяться на попадание в допустимую шкалу критерия.
- **FR-014**: Рейтинг MUST отражать переопределения в тех же полях, что и оценки модели, с
  признаком источника оценки.

### Key Entities

- **Переопределение оценки (ScoreOverride)**: команда, область, критерий, прогон, исходный балл,
  новый балл, комментарий, автор, время, статус (активно/отменено).
- **Пометка проверки (JuryReviewMark)**: команда, прогон, автор, время.
- **Запись журнала (AuditEntry)**: тип действия, объект, автор, время, детали.
- **Член жюри (JuryMember)**: идентификатор и имя для атрибуции действий.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Переопределение оценки занимает у члена жюри менее 30 секунд.
- **SC-002**: 100% переопределений содержат комментарий — иначе операция не проходит.
- **SC-003**: Исходная оценка модели доступна в 100% случаев после переопределения.
- **SC-004**: Итоговый балл после переопределения пересчитывается и совпадает с ручным расчётом
  по весам рубрики.
- **SC-005**: Список «требуют ревью» полностью закрывается пометками жюри — остаток виден в один
  клик.
- **SC-006**: По журналу действий можно восстановить, кто и почему изменил любую оценку.

## Assumptions

- Фича реализуется последней и может быть сокращена: минимально достаточный объём —
  переопределение с комментарием и отображение обеих оценок.
- Авторизация жюри — простейший механизм, достаточный для хакатона (общий токен или список
  пользователей), общий с фичей 004.
- Число членов жюри — единицы; сложная ролевая модель не требуется.
- Переопределения не отправляются обратно в модель и не влияют на калибровку автоматически.

## Dependencies

- **001-evaluation-contract**: структура оценок (блокирующая).
- **003-runner-ingestion**: расчёт итогов, история прогонов.
- **004-api**: эндпойнты жюри и авторизация.
- **005-leaderboard**, **006-team-details**: места отображения оценок жюри.
