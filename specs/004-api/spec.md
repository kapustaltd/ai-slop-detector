# Feature Specification: API платформы

**Feature Branch**: `004-api`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "REST API для UI: рейтинг команд, сводка команды, drill-down в критерий, рубрики, статистика по критериям, перезапуск оценки жюри."

## Overview

API — единственный источник данных для UI. Он отдаёт уже вычисленные значения (итоги, медианы,
позиции в рейтинге) и никогда не пересчитывает их в момент запроса по-другому, чем это сделал
ingestion. API разрабатывается на фикстурах контракта 001 и не ждёт готовности скиллов и runner.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Данные для рейтинга (Priority: P1)

Главная страница запрашивает список команд с итоговым баллом, баллами по областям, статусом и
временем последней оценки — одним запросом, без доп. обращений на каждую команду.

**Why this priority**: рейтинг — главный экран платформы.

**Independent Test**: наполнить хранилище фикстурами и получить корректный список команд.

**Acceptance Scenarios**:

1. **Given** команды с завершёнными оценками, **When** запрашивается список, **Then** возвращаются
   итог, frontend, backend, статус и время оценки по каждой команде.
2. **Given** команда со статусом `needs_review`, **When** запрашивается список, **Then** этот
   признак присутствует в ответе.
3. **Given** команда без завершённой оценки, **When** запрашивается список, **Then** она
   присутствует со статусом и без выдуманных баллов.
4. **Given** запрос с сортировкой и фильтрами, **When** он выполняется, **Then** результат
   соответствует параметрам.

---

### User Story 2 - Сводка по команде (Priority: P1)

Страница команды запрашивает сводку: баллы по каждому критерию для обеих областей, распределение
находок по типам и серьёзности, метаданные прогона.

**Why this priority**: второй по важности экран; без него нет drill-down.

**Independent Test**: запросить сводку по фикстурной команде и сверить с содержимым фикстуры.

**Acceptance Scenarios**:

1. **Given** команда с оценками обеих областей, **When** запрашивается сводка, **Then**
   возвращаются баллы по всем критериям обеих областей.
2. **Given** та же сводка, **When** смотрят метаданные, **Then** доступны SHA, версии скилла,
   рубрики и модели, время оценки.
3. **Given** оценка с переопределением жюри, **When** запрашивается сводка, **Then** видны и
   исходный балл модели, и балл жюри.
4. **Given** несуществующая команда, **When** запрашивается сводка, **Then** возвращается ошибка
   «не найдено», а не пустой объект.

---

### User Story 3 - Drill-down в критерий (Priority: P1)

Пользователь раскрывает критерий и получает: балл, краткий вывод, развёрнутое обоснование,
описание критерия с якорями рубрики и список находок со сниппетами кода и постоянными ссылками.

**Why this priority**: это и есть главная ценность платформы — объяснимость оценки.

**Independent Test**: запросить один критерий фикстурной команды и проверить полноту ответа.

**Acceptance Scenarios**:

1. **Given** команда и критерий, **When** запрашивается детализация, **Then** возвращаются балл,
   `summary`, `rationale`, находки со сниппетами и ссылками.
2. **Given** находка с невалидной ссылкой на код, **When** запрашивается детализация, **Then**
   находка возвращается с явной пометкой о непроверенной ссылке.
3. **Given** критерий, которого нет в рубрике команды, **When** запрашивается детализация,
   **Then** возвращается ошибка «не найдено».

---

### User Story 4 - Описание рубрики («как оценивается») (Priority: P2)

UI показывает, как именно оценивается критерий: описание и якоря уровней. Данные приходят из API
по версии рубрики, зафиксированной в оценке.

**Why this priority**: делает баллы понятными без чтения репозитория платформы.

**Independent Test**: запросить рубрику по версии и сверить с YAML-файлом.

**Acceptance Scenarios**:

1. **Given** версия рубрики, **When** она запрашивается, **Then** возвращаются критерии с весами,
   описаниями и якорями уровней.
2. **Given** несуществующая версия рубрики, **When** она запрашивается, **Then** возвращается
   ошибка «не найдено».

---

### User Story 5 - Статистика по критериям (Priority: P2)

UI сравнивает команду со всеми остальными: медианы и средние по каждому критерию.

**Why this priority**: нужна для radar- и bar-графиков страницы команды.

**Independent Test**: наполнить фикстурами несколько команд и проверить вычисленные медианы.

**Acceptance Scenarios**:

1. **Given** несколько команд с оценками, **When** запрашивается статистика, **Then** по каждому
   критерию возвращаются медиана и среднее.
2. **Given** команды со статусом `failed`, **When** считается статистика, **Then** они не влияют
   на медианы.
3. **Given** менее двух оценённых команд, **When** запрашивается статистика, **Then** ответ явно
   помечает недостаточность данных вместо выдачи вводящих в заблуждение чисел.

---

### User Story 6 - Перезапуск оценки жюри (Priority: P3)

Жюри перезапускает оценку команды: ставит задачу в очередь и видит смену статуса.

**Why this priority**: удобство для жюри; основной поток работает и без него.

**Independent Test**: вызвать перезапуск и проверить появление задачи в очереди.

**Acceptance Scenarios**:

1. **Given** команда с завершённой оценкой, **When** жюри запускает перезапуск, **Then** создаётся
   новая задача, статус становится `pending`, прежние данные сохраняются.
2. **Given** уже выполняющийся прогон той же команды, **When** запрашивается перезапуск, **Then**
   дубликат не создаётся.
3. **Given** запрос перезапуска без прав жюри, **When** он выполняется, **Then** он отклоняется.

---

### Edge Cases

- Хранилище пустое (ни одной оценки) → список возвращается пустым с корректным ответом, UI
  показывает состояние «нет данных».
- Команда оценена только по одной области → в ответе явно видно, что второй области нет.
- Запрос критерия команды, оценённой старой версией рубрики → отдаётся рубрика той версии, по
  которой ставилась оценка, а не текущая.
- Очень длинное обоснование или много находок → ответ ограничивается разумным размером с
  пагинацией находок.
- Одновременный запрос данных во время перезаписи оценки → отдаётся последняя целостная версия.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: API MUST предоставлять список команд с итоговым баллом, баллами по областям,
  статусом, признаком `needs_review` и временем последней оценки.
- **FR-002**: API MUST поддерживать сортировку и фильтрацию списка команд.
- **FR-003**: API MUST предоставлять сводку по команде: баллы по критериям обеих областей,
  распределение находок по `kind` и `severity`, метаданные прогона.
- **FR-004**: API MUST предоставлять детализацию по критерию команды: балл, `summary`,
  `rationale`, находки со сниппетами и постоянными ссылками.
- **FR-005**: API MUST предоставлять описание рубрики по версии: критерии, веса, описания, якоря.
- **FR-006**: API MUST предоставлять статистику по критериям (медиана и среднее) по всем
  оценённым командам.
- **FR-007**: API MUST предоставлять эндпойнт перезапуска оценки команды, доступный только жюри.
- **FR-008**: API MUST отдавать уже вычисленные баллы и MUST NOT пересчитывать их в момент
  запроса по иной формуле, чем ingestion.
- **FR-009**: API MUST возвращать вместе с оценкой версии схемы, рубрики, скилла и модели.
- **FR-010**: Ответы API MUST быть согласованы с типами, сгенерированными из схемы контракта 001.
- **FR-011**: API MUST возвращать осмысленные коды ошибок: «не найдено» для отсутствующих
  сущностей, «конфликт» для дублирующего перезапуска, «нет прав» для действий жюри.
- **FR-012**: API MUST отличать «данных нет» от «оценка не удалась» и от «оценка выполняется».
- **FR-013**: API MUST отдавать находки с невалидными ссылками на код с явной пометкой, а
  MUST NOT скрывать их.
- **FR-014**: API MUST отдавать переопределённые жюри оценки вместе с исходными оценками модели.
- **FR-015**: Эндпойнты чтения MUST быть доступны без авторизации для зрителей рейтинга, а
  действия жюри MUST требовать авторизации [NEEDS CLARIFICATION: рейтинг публичный для всех
  участников или доступен только жюри?].
- **FR-016**: API MUST поддерживать пагинацию для списков находок.
- **FR-017**: API MUST быть документирован машиночитаемой спецификацией, по которой UI может
  генерировать клиент.

### Key Entities

- **Строка рейтинга (LeaderboardRow)**: команда, позиция, итог, баллы по областям, статус, флаги,
  время оценки.
- **Сводка команды (TeamSummary)**: команда, оценки по областям, баллы по критериям, распределение
  находок, метаданные.
- **Детализация критерия (CriterionDetail)**: балл, вывод, обоснование, описание и якоря критерия,
  список обогащённых находок.
- **Описание рубрики (RubricView)**: версия, критерии, веса, описания, якоря.
- **Статистика по критерию (CriterionStats)**: критерий, медиана, среднее, число команд в выборке.
- **Запрос перезапуска (ReevaluationRequest)**: команда, инициатор, время, созданная задача.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: UI собирает рейтинг одним запросом, а страницу команды — не более чем тремя.
- **SC-002**: Ответ на запрос рейтинга приходит менее чем за 300 мс на данных хакатона (десятки
  команд).
- **SC-003**: 100% эндпойнтов покрыты контрактными тестами на фикстурах.
- **SC-004**: UI полностью работает на фикстурах без запущенного runner.
- **SC-005**: Любое расхождение ответа API с типами из схемы падает в тестах.
- **SC-006**: Для каждого состояния (нет данных, идёт оценка, ошибка, требуется ревью) есть
  однозначное представление в ответе API.

## Assumptions

- Набор эндпойнтов соответствует таблице из плана (раздел 4, фича 004) и может быть расширен без
  смены контракта отчёта.
- Хранилище на хакатоне — встраиваемая БД (SQLite достаточно).
- Авторизация жюри реализуется простейшим механизмом, достаточным для хакатона (общий токен или
  список пользователей), без полноценной системы ролей.
- Масштаб данных: десятки команд, сотни оценок, тысячи находок.
- Формат обмена — JSON, совместимый со схемой контракта.

## Dependencies

- **001-evaluation-contract**: схема и фикстуры (блокирующая).
- **003-runner-ingestion**: реальные данные (для продакшн-режима; разработка идёт на фикстурах).
