# Research: 005-leaderboard

Технических «unknowns» в Technical Context нет — стек и данные зафиксированы спекой 008 и уже
частично реализованы. Ниже — решения по расхождениям макета и по структуре компонентов,
принимаемые в рамках этой фичи.

## Макет vs FR (см. plan.md «Расхождения макета с FR — решено»)

- **Decision**: поиск по названию и выгрузка CSV не реализуются в этой фиче.
  **Rationale**: не входят ни в один FR/SC спеки 005; добавление CSV — новая операция экспорта,
  которой нет в контракте и в объёме read-only интерфейса.
  **Alternatives considered**: реализовать по макету как «часть композиции» — отклонено правилом
  «не расширять объём молча» (CLAUDE.md).

- **Decision**: сортировка — только кликом по заголовку колонки (десктоп) и одним select-контролом
  в тулбаре (мобильный, где заголовков нет). Дублирующий dropdown «Сортировка: Итог» на десктопе не
  собирается.
  **Rationale**: FR-007 требует сортировку по каждой числовой колонке; клик по заголовку уже
  закрывает это требование, второй контрол — дублирование поведения без новой функции.

- **Decision**: статус «не удалось» показывает причину, время попытки и текстовую подсказку с
  командой пайплайна для оператора; кнопки повтора нет.
  **Rationale**: прямой ответ владельца продукта (Q14, `docs/open-questions.md`, 2026-09-22) —
  платформа собирает статический бандл в билд, «повтор» в интерфейсе не имеет смысла в этой
  архитектуре. Фича 011 (веб-runner), которая добавляла control plane для такой кнопки, отозвана
  тем же решением (`specs/011-web-runner/spec.md`, Withdrawn).

- **Decision**: сводная строка рубрики («Итог = 0.5 × backend + 0.5 × frontend», число
  категорий/метрик, версии рубрик per area) не выводится.
  **Rationale**: `LeaderboardIndexBundle.meta` не содержит разбивки версий рубрики по area и
  счётчиков категорий/метрик — таких полей нет в индексе (004 FR-002/FR-003, тот же принцип, что
  уже применён к «низкой уверенности» в `docs/design-deviations.md`, пункт 3). Добавление полей —
  через контракт 004, не через эту фичу.

## Загрузка данных: почему нет skeleton/spinner

**Decision**: не показывать skeleton или spinner на первичной загрузке; `isLoading` в текущем коде
относится только к explicit retry после ошибки чтения бандла.

**Rationale**: `shared/api/bundle.ts` читает индекс синхронно через `import.meta.glob(..., { eager:
true })` — он уже в основном чанке на момент рендера первого кадра, промежуточного состояния
«загружается» физически не существует. DESIGN.md прямо запрещает скелетоны/спиннеры на переходах:
«данные статичны и загружены на старте». FR-012 («страница MUST показывать состояния загрузки и
ошибки») закрывается тем, что единственное реальное асинхронное состояние — повторное чтение после
ошибки (`BundleError`, например при отсутствии/несовместимой версии `index.json`), и для него
`aria-busy` + текст уже есть.

**Alternatives considered**: искусственная задержка/скелетон для соответствия макету — отклонено,
описанное в макете «мгновенное» состояние не проходит по правилу «Чего не делать» DESIGN.md.

## Таблица: @tanstack/react-table vs ручная сортировка

**Decision**: оставить текущую ручную сортировку (`Array.prototype.sort` с детерминированным
tie-break по `team_id`), не подключать `@tanstack/react-table` для этой фичи.

**Rationale**: `@tanstack/react-table` уже есть в зависимостях (видимо, под будущий drill-down 006),
но для таблицы из ~7 колонок и десятков строк без пагинации/виртуализации он не даёт ничего сверх
текущей логики, а добавляет слой абстракции и API, которого нет в макете (макет — обычная `<table>`
с ручными `aria-sort`). Решение переносится в `entities/team/model` как чистая функция, тестируется
модульно (принцип VIII).
**Alternatives considered**: `@tanstack/react-table` — отклонено по простоте; оставлено как
кандидат для 006, если там понадобится группировка/вложенные строки дерева таксономии.

## Мобильная раскладка: медиа-запрос vs JS-детект ширины

**Decision**: переключение между `<table>` (десктоп) и списком карточек (мобильный, <640px) —
через Tailwind-брейкпоинт (`hidden md:block` / `md:hidden`), оба варианта рендерятся всегда и
скрываются CSS, без JS-детекта `window.innerWidth`.

**Rationale**: избегает гидратации/layout shift, не требует ResizeObserver; согласуется с «Вёрстка
держится от 360 px» (web/CLAUDE.md) как чисто CSS-адаптивностью. Оба узла используют одни и те же
данные `teams`, поэтому дублирования логики сортировки/фильтрации нет — только разметка.
**Alternatives considered**: условный рендер по `matchMedia` в JS — отклонено, не нужен для чисто
визуального переключения.

## Причина статуса «не удалось» на рейтинге

**Decision**: бейдж статуса `failed` в рейтинге показывает только сам факт и общее пояснение
(«оценка не удалась — подробности на странице команды») через доступную подсказку (`title` +
`aria-describedby`), без текста конкретной причины. Полная причина, время попытки и подсказка
оператору с командой пайплайна — на странице команды (006), не здесь.

**Rationale**: `LeaderboardIndexBundle.teams[]` не содержит поля с текстом причины — только
`status`, `warnings`, `partial` (004 FR-002/003 не включают его в индекс). Требование FR-005/US2
«доступна причина» удовлетворяется переходом на страницу команды, а не дублированием текста в
индексе, которого там нет.

## Словарь предупреждений (`warnings[]`)

**Decision**: карта подписей строится по известным значениям из контракта 001
(`schemas/evaluation-report`): `suspected_prompt_injection` → «Влияние на оценку»,
`repo_too_large` / `file_limit_exceeded` → «Лимит размера», `secret_redacted` → «Секрет скрыт»,
`incomplete_area` → «Область оценена частично», `provider_error` → «Ошибка модели». Неизвестное
значение (например, будущая версия контракта добавит новое) — общий текст «Предупреждение оценки»,
не падение и не скрытие бейджа.

**Rationale**: `LeaderboardIndexBundle.teams[].warnings` типизирован как `string[]` (не как
конкретный union, в отличие от `evaluation-report.ts`), поэтому сопоставление подписей — задача
UI-слоя, а не типов; отсюда явный fallback для непредвиденных значений (принцип IX — не подгонять
типы руками, но и не падать на расширении словаря контрактом).

## FR-014 (спарклайны, P3)

**Decision**: реализуется последней задачей, помечается как вырезаемая первой при нехватке времени
(как и указано в спеке). Требует `TeamArea.categories[].score` из `TeamBundle`, которого нет в
`LeaderboardIndexBundle.teams[].areas` (там только суммарный балл по area, не по категориям) —
то есть спарклайн в рейтинге **не может** быть реализован без похода в файл команды, а FR-014 прямо
запрещает тянуть в спарклайн метрики. Уточнение необходимо: либо спарклайн строится по
`areas.{backend,frontend}` (всего 2 точки — это не «профиль по категориям», а дублирование уже
показанных чисел), либо требует расширения индекса бандла категориями per area (контракт 004).
**Помечено как блокер FR-014, а не как решение** — см. `docs/open-questions.md`.
