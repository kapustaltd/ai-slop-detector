# Feature Specification: Главная страница — рейтинг команд

**Feature Branch**: `005-leaderboard`

**Created**: 2026-09-21

**Status**: Draft

**Input**: User description: "Главная: таблица рейтинга — место, команда, итог, frontend, backend, статус, бейдж needs_review, сортировка и фильтры, состояния загрузки/ошибки/нет данных."

## Overview

Рейтинг — витрина платформы. За пять секунд человек должен понять, кто где стоит, кому нужна
проверка жюри и какие оценки ещё не готовы. Страница строится на данных API и разрабатывается на
фикстурах контракта 001.

## Clarifications

### Session 2026-09-21

- Q: Рейтинг статичный после дедлайна или живой? → A: живой — данные обновляются по ходу
  хакатона, страница показывает свежесть данных и изменение позиций между циклами.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотр рейтинга (Priority: P1)

Участник или зритель открывает главную и видит таблицу команд, отсортированную по итоговому баллу:
место, название, итог, баллы по frontend и backend, статус оценки.

**Why this priority**: это то, ради чего открывают платформу.

**Independent Test**: открыть страницу на фикстурных данных и убедиться, что порядок и числа
соответствуют данным.

**Acceptance Scenarios**:

1. **Given** несколько оценённых команд, **When** открывается главная, **Then** команды
   отсортированы по убыванию итогового балла с проставленными местами.
2. **Given** команды с равным итоговым баллом, **When** строится рейтинг, **Then** они получают
   одинаковое место, а порядок между ними детерминирован и стабилен между обновлениями.
3. **Given** команда с оценкой только одной области, **When** она отображается, **Then** пустая
   область показана как «нет данных», а не как ноль баллов.
4. **Given** клик по строке команды, **When** он выполняется, **Then** происходит переход на
   страницу этой команды.

---

### User Story 2 - Видимость статусов и флагов (Priority: P1)

Жюри и участники видят, какие оценки завершены, какие идут, какие упали и какие требуют внимания
жюри — без необходимости заходить в каждую команду.

**Why this priority**: рейтинг без статусов вводит в заблуждение — низкий балл и незавершённая
оценка выглядят одинаково.

**Independent Test**: подготовить фикстуры со всеми статусами и проверить их отображение.

**Acceptance Scenarios**:

1. **Given** команда со статусом `needs_review`, **When** открывается рейтинг, **Then** у неё
   виден соответствующий бейдж.
2. **Given** команда со статусом `running`, **When** открывается рейтинг, **Then** видно, что
   оценка выполняется, а баллы не показываются как окончательные.
3. **Given** команда со статусом `failed`, **When** открывается рейтинг, **Then** видно, что
   оценка не удалась, и доступна причина.
4. **Given** наведение на бейдж, **When** оно происходит, **Then** показывается пояснение, что
   означает статус.

---

### User Story 3 - Сортировка и фильтры (Priority: P2)

Жюри сортирует рейтинг по любой колонке и фильтрует по статусу, чтобы, например, быстро найти все
команды, требующие ручной проверки.

**Why this priority**: рабочий инструмент жюри; полезен, но не блокирует просмотр.

**Independent Test**: применить каждую сортировку и фильтр на фикстурах и сверить результат.

**Acceptance Scenarios**:

1. **Given** рейтинг, **When** пользователь сортирует по колонке backend, **Then** порядок строк
   меняется соответственно, а места остаются привязанными к итоговому баллу.
2. **Given** фильтр по статусу `needs_review`, **When** он применён, **Then** отображаются только
   такие команды и видно, что фильтр активен.
3. **Given** активные фильтры, **When** страница перезагружается по ссылке, **Then** состояние
   фильтров сохраняется.
4. **Given** фильтр, под который не попадает ни одна команда, **When** он применён, **Then**
   показывается понятное пустое состояние с возможностью сбросить фильтр.

---

### User Story 4 - Состояния страницы (Priority: P2)

Пользователь всегда понимает, что происходит: данные загружаются, данных ещё нет, произошла
ошибка загрузки.

**Why this priority**: на хакатоне страница часто открывается до появления данных.

**Independent Test**: смоделировать каждое состояние и проверить отображение.

**Acceptance Scenarios**:

1. **Given** идёт загрузка данных, **When** страница открыта, **Then** показывается индикатор
   загрузки, а не пустая таблица.
2. **Given** ни одной оценки нет, **When** страница открыта, **Then** показывается состояние «нет
   данных» с пояснением.
3. **Given** API недоступен, **When** страница открыта, **Then** показывается ошибка с
   возможностью повторить запрос.

---

### User Story 5 - Мини-спарклайны по критериям (Priority: P3)

В строке команды виден компактный профиль оценок по критериям, чтобы сравнивать команды не только
по итогу.

**Why this priority**: приятное дополнение, вырезается первым при нехватке времени.

**Independent Test**: включить спарклайны на фикстурах и проверить соответствие данным.

**Acceptance Scenarios**:

1. **Given** команда с оценками по критериям, **When** отображается строка, **Then** спарклайн
   отражает профиль баллов.
2. **Given** команда без завершённой оценки, **When** отображается строка, **Then** спарклайн не
   рисуется.

---

### Edge Cases

- Очень длинное название команды → усечение с подсказкой, вёрстка не ломается.
- Много команд (сотни строк) → таблица остаётся отзывчивой, при необходимости применяется
  виртуализация или пагинация.
- Оценка обновилась, пока страница открыта → доступно обновление данных без ручной перезагрузки.
- Узкий экран (телефон жюри) → таблица остаётся читаемой, ключевые колонки не теряются.
- Команда без оценок вообще → присутствует в списке в конце с состоянием «нет данных».

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Страница MUST отображать таблицу команд с колонками: место, команда, итог, frontend,
  backend, статус.
- **FR-002**: Страница MUST отображать бейдж `needs_review` для команд, помеченных к ручной
  проверке.
- **FR-003**: Места MUST рассчитываться по итоговому баллу, а одинаковые баллы MUST получать
  одинаковое место.
- **FR-004**: Порядок команд с равными баллами MUST быть детерминированным.
- **FR-005**: Страница MUST различать визуально «нет данных», «оценка выполняется», «оценка не
  удалась» и «оценка завершена».
- **FR-006**: Страница MUST NOT показывать отсутствующие оценки как нулевые баллы.
- **FR-007**: Страница MUST поддерживать сортировку по каждой числовой колонке.
- **FR-008**: Страница MUST поддерживать фильтрацию по статусу оценки.
- **FR-009**: Состояние сортировки и фильтров MUST отражаться в адресе страницы, чтобы ссылку
  можно было переслать.
- **FR-010**: Клик по строке MUST вести на страницу команды.
- **FR-011**: Страница MUST показывать время последнего завершённого цикла оценки, чтобы была
  видна свежесть живого рейтинга.
- **FR-011a**: Страница MUST обновлять данные периодически без ручной перезагрузки и показывать,
  что идёт новый цикл оценки.
- **FR-011b**: Страница MUST показывать изменение позиции команды относительно предыдущего цикла
  (вырос/упал/без изменений).
- **FR-012**: Страница MUST показывать состояния загрузки и ошибки с возможностью повтора.
- **FR-013**: Страница MUST NOT выполнять собственных вычислений итоговых баллов — только
  отображать значения, пришедшие из API (принцип VI конституции).
- **FR-014**: Страница SHOULD показывать мини-спарклайны профиля критериев (низкий приоритет).
- **FR-015**: Страница MUST оставаться пригодной к использованию на экране шириной от 360 px.

### Key Entities

- **Строка рейтинга**: место, команда, итог, баллы по областям, статус, флаги, время оценки.
- **Состояние таблицы**: активная сортировка, активные фильтры, состояние загрузки.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь определяет тройку лидеров и команды с флагом `needs_review` не более
  чем за 5 секунд после открытия страницы.
- **SC-002**: Страница отрисовывается менее чем за 1 секунду на данных хакатона.
- **SC-003**: Все пять состояний (загрузка, нет данных, ошибка, в процессе, готово) имеют
  различимое представление и покрыты тестами.
- **SC-004**: Фильтр «требуют ревью» позволяет жюри получить список проверки в один клик.
- **SC-005**: Ссылка с применёнными фильтрами открывается у другого человека в том же виде.
- **SC-006**: Страница полностью работает на фикстурах без запущенного runner.

## Assumptions

- Пользователи рейтинга: жюри, участники, зрители; отдельных ролей на этой странице нет, кроме
  доступа к действиям жюри.
- Масштаб — десятки команд; виртуализация таблицы не требуется, но вёрстка не должна ломаться на
  сотнях строк.
- Данные приходят из API фичи 004; на этапе разработки — из фикстур контракта 001.
- Автообновление данных — периодический опрос, реальное время не требуется; режим живого рейтинга
  подтверждён владельцем продукта (Q2).

## Dependencies

- **001-evaluation-contract**: фикстуры и структура данных (блокирующая).
- **004-api**: источник данных в рабочем режиме.
