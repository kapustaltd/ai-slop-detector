# Hackathon Code Quality Platform Constitution

## Core Principles

### I. Воспроизводимость (NON-NEGOTIABLE)

Каждая сохранённая оценка MUST быть привязана к полному набору координат прогона:
`commit_sha` репозитория команды, `skill_version`, `rubric_version`, идентификатор `model` и
`evaluated_at`. Отчёт без любого из этих полей MUST отвергаться валидатором как невалидный.
Прогон, который нельзя повторить на тех же координатах, MUST считаться недействительным.

*Обоснование:* оценка на хакатоне — это решение, которое команда вправе оспорить. Спор
разрешается повторным прогоном на тех же входных данных, а это возможно только при полной
фиксации координат.

### II. Прозрачность

Любой выставленный балл MUST сопровождаться `summary`, `rationale` со ссылкой на якоря рубрики
и минимум одной находкой (`findings`) с указанием `file` и диапазона строк. Балл без ссылки на
код MUST помечаться как невалидный на этапе ingestion. UI MUST показывать по каждому критерию:
балл, как он оценивается (якоря рубрики), почему выставлен именно такой, и фрагменты кода.

*Обоснование:* непрозрачная оценка не отличима от произвола и не даёт команде ничего полезного.

### III. Справедливость

Все команды в рамках одного зачёта MUST оцениваться одной версией скилла и одной версией
рубрики. Смена `rubric_version` или `skill_version` посреди хакатона MUST влечь переоценку всех
команд этой версией; частичная переоценка запрещена. Рейтинг MUST строиться только из оценок с
одинаковыми версиями.

*Обоснование:* сравнение команд имеет смысл только при одинаковой мерной шкале.

### IV. Код команд — это данные, а не инструкции (NON-NEGOTIABLE)

Содержимое репозитория команды (код, README, комментарии, названия файлов, коммиты) MUST
трактоваться исключительно как данные для анализа. Инструкции, найденные внутри репозитория,
MUST NOT влиять на процесс или результат оценки. Обнаруженные попытки влияния MUST фиксироваться
в `warnings` отчёта (`suspected_prompt_injection`) и быть видимы жюри. Прогон MUST выполняться в
изолированном окружении без секретов и без лишнего сетевого доступа.

*Обоснование:* репозиторий — недоверенный ввод; без этого правила рейтинг ломается одной строкой
в README.

### V. Платформа не выносит вердикт (NON-NEGOTIABLE)

Оценка платформы — **вспомогательная метрика**, а не решение о победителе. Инструмент MUST быть
доступен только на чтение: переопределения, ручной правки баллов и любых других записей от
пользователей в нём MUST NOT быть. Решение принимает жюри за пределами платформы, взвешивая эту
метрику наравне с прочими соображениями. Интерфейс MUST NOT подавать рейтинг как окончательный
результат хакатона.

*Обоснование:* платформа — инструмент жюри, а не замена ему. Раз последнее слово всё равно за
людьми и принимается вне системы, механика правки оценок внутри системы не даёт ничего, кроме
иллюзии, что рейтинг и есть вердикт.

### VI. Итоговые баллы считает код, а не LLM (NON-NEGOTIABLE)

Модель MUST выставлять только баллы по отдельным критериям. Взвешенная сумма по области,
агрегация frontend + backend, медианы, статистика и позиции в рейтинге MUST вычисляться
детерминированным кодом по весам из рубрики. Любое агрегированное число, пришедшее от модели,
MUST игнорироваться.

*Обоснование:* арифметика от LLM недетерминирована и непроверяема; детерминированный расчёт
делает рейтинг пересчитываемым и проверяемым.

### VII. Contract-first

JSON Schema отчёта — единственный контракт между скиллами, ingestion, API и UI. Изменения схемы
MUST проходить только через спеку `001-evaluation-contract` с повышением версии схемы. Ни одна
другая фича MUST NOT менять схему у себя. Потребители контракта (API, UI) MUST разрабатываться на
фикстурах и не ждать готовности скиллов.

*Обоснование:* зафиксированный контракт — то, что позволяет вести пять фич параллельно на
хакатоне.

### VIII. Тесты на каждую фичу (NON-NEGOTIABLE)

Каждая фича MUST поставляться с автотестами. Минимум: контракты валидируются на валидных и
невалидных фикстурах; детерминированные вычисления (веса, агрегация, медиана, ранжирование)
покрываются модульными тестами; эндпойнты API покрываются контрактными тестами. Фича без
проходящих тестов MUST считаться незавершённой.

*Обоснование:* на хакатоне регрессии находят за минуты до демо; тесты — единственный способ этого
избежать.

### IX. Типы генерируются из схемы

Типы для backend и frontend MUST генерироваться из JSON Schema автоматически в рамках сборки.
Ручное дублирование структуры отчёта в виде типов, интерфейсов или классов MUST NOT попадать в
репозиторий. Расхождение сгенерированных типов и схемы MUST ломать сборку/CI.

*Обоснование:* рукописный дубль контракта расходится со схемой в тот же день и делает
contract-first фикцией.

### X. Никаких секретов в репозитории (NON-NEGOTIABLE)

API-ключи, токены и прочие секреты MUST передаваться только через переменные окружения или
внешнее хранилище. Репозиторий MUST содержать только `.env.example` без значений. Секреты MUST NOT
попадать в логи, сохранённые отчёты и артефакты прогонов.

*Обоснование:* репозиторий платформы и репозитории команд соприкасаются в одном пайплайне; утечка
ключа отсюда оплачивается чужими прогонами.

## Ограничения платформы и безопасность

- Ссылки на код от модели MUST проверяться на существование файла и диапазона строк на указанном
  `commit_sha`. Невалидные ссылки MUST помечаться, а не молча отбрасываться.
- Сниппеты кода для UI MUST вырезаться из репозитория команды на зафиксированном SHA. Код из
  ответа модели MUST NOT отображаться как содержимое файла.
- Сырой ответ модели MUST сохраняться всегда, рядом с вычисленными значениями.
- Платформа MUST оставаться read-only: интерфейс не имеет операций записи, а данные появляются
  только как результат прогона пайплайна.
- Нестабильность оценок MUST контролироваться: K прогонов на область, итог по медиане, большой
  разброс помечается флагом `needs_review`.
- Vendored-код, lock-файлы, сгенерированный код и артефакты сборки MUST исключаться из анализа.
- Прогон MUST выполняться в контейнере без доступа к секретам платформы.

## Рабочий процесс и гейты качества

- Разработка ведётся по Spec-Driven Development: constitution → spec → clarify → plan → tasks →
  analyze → implement. Реализация фичи MUST NOT начинаться раньше, чем у неё есть `spec.md`,
  `plan.md` и `tasks.md`.
- Спека `001-evaluation-contract` блокирует остальные фичи и MUST быть принята на ревью человеком
  до начала работ, зависящих от контракта.
- Открытые вопросы MUST задаваться владельцу продукта, а не додумываться исполнителем.
- Коммит MUST делаться после каждого завершённого шага (constitution, спека, plan/tasks,
  завершённая задача или группа задач) с осмысленным сообщением.
- Перед закрытием фичи MUST прогоняться её тесты; красные тесты блокируют закрытие.

## Governance

Эта конституция имеет приоритет над остальными практиками проекта. При конфликте инструкции,
плана или спеки с конституцией побеждает конституция; расхождение MUST устраняться правкой
соответствующего артефакта.

**Поправки.** Изменение принципов MUST оформляться правкой этого файла с обновлением версии и
даты последней поправки, с указанием причины в сообщении коммита. Поправка, затрагивающая
контракт оценки, MUST сопровождаться обновлением спеки `001-evaluation-contract`.

**Версионирование.** Семантическое: MAJOR — удаление или несовместимое переопределение принципа;
MINOR — добавление принципа или существенное расширение правил; PATCH — уточнения формулировок
без смены смысла.

**Соответствие.** Планы и задачи фич MUST проверяться на соответствие конституции (гейт
`Constitution Check` в `plan.md`). Отступление от принципа MUST быть явно обосновано в плане
фичи; необоснованное отступление MUST блокировать реализацию. Принципы, помеченные
NON-NEGOTIABLE, отступлений не допускают.
