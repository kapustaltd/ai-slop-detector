# Изменение контракта

Контракт — это то, что связывает скиллы оценки, пайплайн и интерфейс. Его правка задевает всех
потребителей сразу, поэтому порядок действий жёсткий.

## Что считается контрактом

| Артефакт | Владелец | Где описан |
|---|---|---|
| JSON Schema отчёта | спека 001 | `specs/001-evaluation-contract/spec.md` |
| `rubrics/backend.v1.yaml`, `rubrics/frontend.v1.yaml` | спека 001 | там же |
| Таксономия и веса | `docs/rubric-proposal.md` | — |
| Схема дата-бандла | спека 004 | `specs/004-data-bundle/spec.md` |

Схему отчёта не правит никакая фича, кроме 001 (инвариант 2 в `CLAUDE.md`).

## Порядок

1. **Сначала спека.** Внеси изменение в `specs/001-evaluation-contract/spec.md` (или 004 для
   бандла): требование, затронутые Acceptance Scenarios, запись в `## Clarifications`.
2. **Версия.** Несовместимое изменение — новая мажорная версия схемы и новая версия рубрики
   (`backend.v2`). Совместимое — минорная. Версия указывается внутри самого отчёта.
3. **Рубрика.** Правка таксономии начинается с `docs/rubric-proposal.md`, оттуда переносится в
   YAML. Проверь суммы: веса категорий = 1.0, подкатегорий внутри категории = 1.0, метрик внутри
   подкатегории = 1.0, сумма эффективных весов = 1.0.
4. **Фикстуры.** Обнови валидные и невалидные фикстуры: невалидная фикстура должна падать по той
   причине, ради которой существует.
5. **Типы.** Перегенерируй типы для Go и TypeScript. Руками типы не правятся — расхождение должно
   ломать CI, а не чиниться вручную.
6. **Потребители.** Пройди по `rg "<изменённое поле>" web/ specs/` и обнови всех.
7. **Переоценка.** Смена версии рубрики означает переоценку всех команд — частичная запрещена
   принципом справедливости (конституция, принцип III).
8. **Коммит.** `contract: <что изменилось и какая версия>`.

## Цена изменений

- **Дёшево:** веса. Переоценки не требуют — агрегаты пересчитываются из сохранённых сырых отчётов
  режимом пересчёта пайплайна.
- **Дорого:** состав метрик, их `id` и смысл. Требуют новой версии рубрики и переоценки всех
  команд.
- **Очень дорого:** структура отчёта. Задевает скиллы, пайплайн, бандл и интерфейс.

`id` метрики стабилен: изменился смысл — заводится новый `id`, старый не переиспользуется.

## Запреты

1. Не добавляй в схему отчёта поля с агрегированными баллами: подкатегории, категории, области и
   итог считает код.
2. Не правь сгенерированные типы вручную.
3. Не меняй рубрику посреди прогона: в одном дата-бандле допустима только одна версия рубрики.
4. Не снижай строгость схемы, чтобы «прошёл» невалидный вывод модели — чини скилл или пайплайн.
