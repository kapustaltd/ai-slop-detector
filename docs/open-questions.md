## Q1. Стек платформы — ОТВЕЧЕН

Планом не был зафиксирован (раздел 7, п. 4). Решение владельца продукта от 2026-09-21:

- **Backend (API + runner): Go**
- **Frontend: React + TypeScript**
- **Хранилище: PostgreSQL**

Следствия, которые фиксируются в `plan.md` фич 003 и 004:

- Типы генерируются из JSON Schema контракта 001 в двух направлениях: Go-структуры и
  TypeScript-типы. Инструменты генерации выбираются в `plan.md` фичи 001; требование конституции
  (принцип IX) — генерация в сборке и проверка дрейфа в CI.
- Runner на Go запускает Claude в headless-режиме внешним процессом (`claude -p` со скиллом);
  Claude Agent SDK для Go отсутствует, поэтому взаимодействие идёт через CLI и JSON на stdout.
- PostgreSQL вместо встраиваемой БД: нужны docker-compose для локального запуска и миграции;
  зато история прогонов и конкурентные прогоны обходятся без ухищрений.

Открытых подвопросов нет.

## Q2. Режим запуска оценки — ОТВЕЧЕН

Раздел 7, п. 1. Решение владельца продукта от 2026-09-21: **периодические прогоны по ходу
хакатона, живой рейтинг**.

Следствия, внесённые в спеки:

- 003: цикл оценки фиксирует текущий SHA отслеживаемой ветки каждой команды (FR-027a), история
  оценок хранится по SHA (FR-027b), неизменившиеся репозитории не переоцениваются (FR-027c),
  история доступна для графика динамики (FR-027d), периодичность настраивается и цикл
  запускается вручную (FR-027e), рейтинг строится по последним завершённым оценкам (FR-027f).
  Новые сущности: `EvaluationCycle`, `EvaluationHistoryPoint`.
- 004: эндпойнты истории оценок и времени последнего цикла (FR-018 — FR-020).
- 005: свежесть данных, автообновление, изменение позиции между циклами (FR-011, FR-011a,
  FR-011b).
- 006: график динамики, выбор точки истории (FR-022 — FR-025), новая User Story 3.
- 007: пометка «проверено жюри» и переопределения привязаны к конкретному прогону.

Бюджет: N команд × 2 области × K прогонов × число циклов. Периодичность подбирается под бюджет —
см. Q9.

## Q3. Формула агрегации frontend + backend — ЧАСТИЧНО ОТВЕЧЕН

Раздел 7, п. 2. Ответ владельца продукта от 2026-09-21: критерии и правила оценки одинаковы для
всех команд, специфика областей заключена только в разделении рубрик на `backend.v1` и
`frontend.v1`. Из этого следует: **формула агрегации не зависит от типа проекта** — вариант с
полем «тип проекта» при сабмите снят (тем более что сабмита нет, см. Q4).

Остаётся два подвопроса:

1. **Веса областей**: 50/50 или иное соотношение (например, backend 0.6 / frontend 0.4)?
2. **Команда с одной областью**: репозитории без фронтенда или без бэкенда встречаются, а путей
   области команды не сообщают (Q4) — их определяет автоматика. Итог такой команды считается по
   имеющейся области, или отсутствующая область идёт в расчёт как ноль?

Второй подвопрос важнее первого: он определяет, окажутся ли чисто бэкендовые проекты внизу
рейтинга по построению.

## Q4. Сабмит проектов — ОТВЕЧЕН

Раздел 7, п. 3. Решение владельца продукта от 2026-09-21: **организаторы забирают репозитории
сами**. Формы сабмита для команд нет.

Следствия, внесённые в спеки:

- 003: реестр команд (репозиторий + отслеживаемая ветка) ведут организаторы (FR-028), реестр
  редактируется оператором без перезапуска (FR-029), доступ к репозиториям — токеном
  организаторов вне репозитория платформы (FR-030), недоступный репозиторий даёт `failed` с
  причиной (FR-031). Новая сущность: `TeamRegistryEntry`.
- 003 FR-005: пути к backend- и frontend-частям определяются автоматически по структуре
  репозитория, с возможностью ручного переопределения оператором для нестандартных монореп —
  команды пути не сообщают.
- 004: эндпойнты управления реестром для оператора (FR-021).

## Q5. Веса критериев в рубриках

План перечисляет критерии, но не задаёт их веса. Нужны веса для `backend.v1` (архитектура,
читаемость, обработка ошибок, дизайн API, работа с данными, безопасность, тесты, конфигурация и
инфраструктура) и для `frontend.v1` (компонентная структура, состояние, типизация,
производительность, доступность, консистентность стилей, тесты).

Допустимый вариант ответа — «равные веса» или «предложи, я скорректирую».

## Q8. Golden set

Откуда берутся 3–4 эталонных репозитория (публичные проекты, прошлогодние работы, специально
подготовленные) и кто и когда согласует ожидаемые диапазоны оценок. Без этого 002 нельзя
откалибровать.

## Q9. K прогонов и порог разброса

В спеках принято по умолчанию: K = 3, флаг `needs_review` при разбросе баллов по критерию больше
порога. Нужно подтвердить K (влияет на стоимость: N × 2 × K вызовов) и задать порог (например,
разброс > 2 баллов).

## Q10. Хостинг репозиториев команд

Постоянные ссылки строятся по шаблону `blob/<sha>/path#L42-L58` — это GitHub-совместимый формат.
Подтвердить, что все репозитории на GitHub, либо назвать другие хостинги (GitLab, self-hosted),
чтобы шаблон ссылки стал настраиваемым.
