## Q11. Архитектура: сервер или статика — ОТВЕЧЕН

Вопрос поднят владельцем продукта 2026-09-21: «зачем нам бэкенд, если скилл генерит данные, а
фронт их показывает».

Решение: **бэкенда и базы данных нет**. Платформа — внутренний инструмент только для просмотра,
оценка в нём вспомогательная метрика, решение жюри принимает вне системы.

Архитектура: **CLI-пайплайн (Go) → статический дата-бандл (JSON) → статический UI (React + TS)**.

Обоснование: прогон однократный (Q2), после него данные неизменны, а интерфейс только читает.
Сервер, отдающий неизменный JSON из базы, — дорогой способ отдать файл. PostgreSQL, REST API,
миграции и серверная аутентификация ушли из объёма; ограничение доступа обеспечивает хостинг.

Следствия:

- 003 переписана как CLI-пайплайн: запуск оператором, вывод — дата-бандл на диске, хранилище —
  файловая система.
- 004 переписана из «REST API» в «Дата-бандл для UI»: контракт набора JSON-файлов (индекс
  рейтинга, файл команды, рубрика, статистика), каталог переименован в `specs/004-data-bundle`.
- 005 и 006 читают бандл напрямую, без API; автообновления нет.
- 007 снята с объёма целиком (см. `specs/007-jury-tools/spec.md`).
- Конституция: принцип V переформулирован, версия 2.0.0.

Сохранено намеренно: скилл отдаёт **JSON по схеме 001**, а не прозу, из которой JSON потом
парсится. Промежуточная проза ломает проверку ссылок `file:line_start-line_end`, на которой
держатся вырезка сниппетов и защита от галлюцинаций.

## Q1. Стек платформы — ОТВЕЧЕН

Планом не был зафиксирован (раздел 7, п. 4). Решение владельца продукта от 2026-09-21:

- **Backend (API + runner): Go**
- **Frontend: React + TypeScript**
- **Хранилище: PostgreSQL**

**Уточнено 2026-09-21 (см. Q11)**: API и PostgreSQL сняты. Go остаётся — как язык CLI-пайплайна;
React + TypeScript остаются — как статический UI; хранилище — файловая система (дата-бандл).

Следствия, которые фиксируются в `plan.md` фич 003 и 004:

- Типы генерируются из JSON Schema контракта 001 в двух направлениях: Go-структуры и
  TypeScript-типы. Инструменты генерации выбираются в `plan.md` фичи 001; требование конституции
  (принцип IX) — генерация в сборке и проверка дрейфа в CI.
- Runner на Go запускает Claude в headless-режиме внешним процессом (`claude -p` со скиллом);
  Claude Agent SDK для Go отсутствует, поэтому взаимодействие идёт через CLI и JSON на stdout.
- PostgreSQL вместо встраиваемой БД: нужны docker-compose для локального запуска и миграции;
  зато история прогонов и конкурентные прогоны обходятся без ухищрений.

Открытых подвопросов нет.

## Q2. Режим запуска оценки — ОТВЕЧЕН

Раздел 7, п. 1. Решение владельца продукта от 2026-09-21: **однократный пакетный прогон после
дедлайна**. Рейтинг собирается после того, как агрегация завершена. Живой рейтинг, периодическая
переоценка по ходу хакатона и график динамики в объём не входят.

Следствия, внесённые в спеки:

- 003: пакетный прогон фиксирует SHA вершины отслеживаемой ветки каждой команды и оценивает именно
  его (FR-027a); рейтинг собирается только после завершения агрегации (FR-027b); прогон
  запускается вручную оператором (FR-027c); перезапуск отдельной команды для жюри сохраняется
  (FR-027d). Новая сущность: `BatchRun`. User Story 6 — пакетный прогон всех команд.
- 004: история прогонов отдаётся для разбора спорных случаев и перезапусков, а не для графика
  динамики (FR-018); рейтинг отдаёт только завершённые оценки (FR-019); отдаётся время завершения
  пакетного прогона (FR-020).
- 005: показывается время завершения прогона (FR-011); изменение позиций между циклами снято.
- 006: график динамики и выбор точки истории сняты — страница показывает одну оценку команды.
- 007: впоследствии снята с объёма целиком (см. Q11).

Бюджет: N команд × 2 области (один прогон на область, см. Q9), плюс запас на повторы упавших.

## Q3. Формула агрегации frontend + backend — ЗАКРЫТ

Раздел 7, п. 2. Ответ владельца продукта: таксономия и правила одинаковы для всех команд,
специфика областей выражена только разделением рубрик. Команды ранжируются по итоговому баллу.
Веса — на усмотрение платформы.

Решение платформы (`docs/rubric-proposal.md`, раздел 4):

- **Веса областей**: backend 0.50 / frontend 0.50.
- **Команда с одной областью**: веса присутствующих областей нормализуются до 1.0 — итог
  считается по тому, что есть; отсутствующая область не учитывается как ноль. Факт частичной
  оценки отражается отдельным признаком в рейтинге (003 FR-021a, 005 FR-003b), чтобы жюри видело
  разницу. Обоснование: пути областей определяет автоматика, команды их не сообщают, поэтому
  «ноль за отсутствие» наказывал бы чисто бэкендовый проект за структуру, а не за качество кода.
- **Ранжирование**: по итоговому баллу по убыванию (003 FR-021b).

Если веса областей или правило неполной оценки нужно поменять — это правка
`docs/rubric-proposal.md` и версии рубрики, переоценки команд она не требует.

## Q4. Сабмит проектов — ОТВЕЧЕН

Раздел 7, п. 3. Решение владельца продукта от 2026-09-21: **организаторы забирают репозитории
сами**. Формы сабмита для команд нет.

Следствия, внесённые в спеки:

- 003: реестр команд (репозиторий + отслеживаемая ветка) ведут организаторы (FR-028), реестр
  редактируется оператором без перезапуска (FR-029), доступ к репозиториям — токеном
  организаторов вне репозитория платформы (FR-030), недоступный репозиторий даёт `failed` с
  причиной (FR-031). Новая сущность: `TeamRegistryEntry`.
- 003 FR-005: пути к backend- и frontend-частям определяются автоматически по структуре
  репозитория, с возможностью ручного переопределения оператором для нестандартных монореп —
  команды пути не сообщают.
- 004: эндпойнты управления реестром для оператора (FR-021).

## Q5. Категории, подкатегории, метрики и веса — ЗАКРЫТ ПРЕДЛОЖЕНИЕМ ПЛАТФОРМЫ

Владелец продукта делегировал таксономию платформе. Предложение целиком лежит в
`docs/rubric-proposal.md`:

- **backend.v1**: 8 категорий, 16 подкатегорий, 27 метрик.
- **frontend.v1**: 7 категорий, 14 подкатегорий, 23 метрики.
- Веса относительные внутри уровня (сумма 1.0 на каждом уровне); эффективный вес метрики —
  произведение трёх весов. Суммы проверены: обе рубрики дают 1.000000.
- Модель оценивает только метрики-листья; подкатегории, категории, области и итог считает код.

Спеки приведены к этой структуре: 001 (рубрика и отчёт), 002 (скилл оценивает метрики), 003
(агрегация снизу вверх), 004 (drill-down и статистика), 005 (спарклайны по категориям), 006
(radar/bar по категориям, drill-down до метрики), 007 (жюри правит только метрики).

**Что ещё можно поменять дёшево**: сами веса. **Что дорого**: состав метрик — его смена требует
новой версии рубрики и переоценки всех команд (принцип III конституции).

## Q7. Публичность рейтинга — ОТВЕЧЕН

Решение владельца продукта от 2026-09-21: платформа — **внутренний административный инструмент**.
Публичного доступа нет, все эндпойнты и страницы требуют авторизации.

Следствия, внесённые в спеки:

- 004: ограничение доступа обеспечивает хостинг — приватный деплой, basic auth или VPN
  (FR-016). Собственной аутентификации и ролей в приложении нет: после ответа на Q11 сервер и
  операции записи из объёма ушли, ограничивать внутри приложения стало нечего.
- 005: страница требует авторизации (FR-003a); формулировки пользователей приведены к
  «организаторы и жюри» вместо «участники и зрители».
- 006: страница требует авторизации (FR-020b).

## Q8. Golden set — ОТВЕЧЕН: формальная калибровка снята

Решение владельца продукта от 2026-09-21: «пускай нейронка просто оценивает, а люди уже с
результатом ревью будут работать» — супер-точность не требуется.

Из объёма убраны: golden set из 3–4 репозиториев, согласованные жюри диапазоны оценок,
автоматический отчёт о расхождениях.

Взамен в 002: разовая **проверка вменяемости** — скилл прогоняется минимум на двух репозиториях
заведомо разного уровня, результат смотрит человек (FR-019). Критерий один: сильный проект должен
получить по большинству категорий больше слабого. Формальная калибровка явно объявлена вне
объёма (FR-020), и платформа не должна заявлять измерительную точность (FR-021).

**Принятый риск:** абсолютные значения баллов не проверены. «7.2 из 10» означает «модель так
решила», а не «измерено». Поэтому интерфейс и не должен подавать балл как вердикт — это же
закреплено принципом V конституции.

## Q9. K прогонов и порог разброса — ОТВЕЧЕН: один прогон

Решение владельца продукта от 2026-09-21: повторные прогоны, медианы и флаги разброса не нужны.

Из объёма убраны: K прогонов на область, медиана по метрикам, порог разброса, статус и флаг
`needs_review` во всех фичах (003, 004, 005, 006).

Что осталось вместо них:

- **Один прогон на область** (003 FR-024). Повторы выполняются только при невалидном по схеме
  выводе — это про валидность, а не про устойчивость.
- **Уровень `confidence`** по каждой метрике: модель сама сообщает, насколько уверена (001).
- **Предупреждения (`warnings`)** оценки — подозрение на prompt injection, превышение лимитов —
  как основание для внимания жюри в рейтинге и на странице команды.

Бюджет прогона уменьшился втрое: N команд × 2 области вместо N × 2 × K.

Конституция приведена в соответствие: из раздела ограничений убрано требование K прогонов и
медианы, добавлено «платформа не претендует на измерительную точность»; версия 2.1.0.

## Q10. Хостинг репозиториев команд — ОТВЕЧЕН

Решение владельца продукта от 2026-09-21: репозитории могут лежать на **GitHub, GitLab и
GitVerse**. Оценивается **только содержимое репозитория** — наличие CI/CD и контейнеризации
определяется по конфигурационным файлам, а не по обращениям к API хостинга.

Следствия, внесённые в спеки:

- 003 FR-021: шаблон постоянной ссылки выбирается под хостинг и задаётся конфигурацией, а не
  зашит в код.
- 003 FR-021a: при неизвестном хостинге находка остаётся без постоянной ссылки, но со сниппетом и
  путём с номерами строк — выдуманная ссылка не генерируется.
- 003 FR-010a и 002 FR-008a: API хостингов не используются; CI/CD и Docker детектируются по
  файлам (`.github/workflows`, `.gitlab-ci.yml`, `Dockerfile`, `compose.yaml` и аналоги).
- `docs/rubric-proposal.md`: описания метрик `ci_pipeline` и `run_reproducibility` приведены к
  файловой детекции; добавлен принцип 6 «оценивается только содержимое репозитория».

Точные форматы якорей строк у каждого хостинга проверяются при реализации на живом примере:
ошибочная ссылка хуже отсутствующей, поэтому непроверенный шаблон не включается.

## Q12. Поиск по названию и выгрузка CSV в рейтинге — ОТВЕЧЕН: не нужны

Поднят при планировании 005 (2026-09-22). Макет `01-leaderboard-light.html` показывает поле
поиска по названию команды и кнопку «Выгрузить CSV» в тулбаре рейтинга. Ни то, ни другое не было
упомянуто ни в одном FR или Success Criteria спеки 005.

Решение владельца продукта от 2026-09-22: **не нужны**. Команд немного — поиск не оправдан;
выгрузка данных из интерфейса не планируется. Оба элемента макета не реализуются, `spec.md` не
меняется (объём и так был закрыт без них).

## Q13. Спарклайны FR-014: данных для них нет в индексе бандла — ожидает ответа

FR-014 (P3, «SHOULD»): мини-спарклайн профиля по категориям в строке рейтинга. Но
`LeaderboardIndexBundle.teams[].areas` — это `{backend: number, frontend: number}`, суммарный
балл по области, а не разбивка по категориям. Профиль по категориям есть только в файле команды
(`TeamBundle.areas[area].categories[]`), который рейтинг не загружает (и не должен — 004 FR-003
запрещает тянуть в индекс лишнее без необходимости).

Варианты: (а) спарклайн строится по двум точкам `backend`/`frontend` — это не «профиль по
категориям», а дублирование уже показанных чисел, вероятно не то, что имелось в виду; (б) индекс
бандла расширяется категориями per area — это правка контракта 004 с повышением версии схемы
(инвариант 2 CLAUDE.md), затрагивает пайплайн 003. Пока FR-014 не реализуется в 005 — это
низкоприоритетная (P3) часть, «вырезается первой при нехватке времени» по тексту самой спеки.

## Q14. Кнопка повтора у статуса «не удалось» — ОТВЕЧЕН: не нужна

История вопроса: `docs/design-deviations.md` какое-то время допускал кнопку повтора условно —
«если создаёт прогон через `/api/v1` фичи 011 (веб-runner)». Но `specs/011-web-runner/spec.md`
сама помечена **Withdrawn (2026-09-22)**: решение владельца продукта в тот же день зафиксировало
другой порядок работы — оператор клонирует репозитории и запускает пайплайн командой в терминале,
без HTTP control plane и веб-формы запуска. Условие «если 011 реализована» стало невыполнимым не
из-за того, что 011 ещё не готова, а потому что её отозвали.

Отдельно Clarification спеки 005 (сессия 2026-09-22) с самого начала отвечала на этот же вопрос
без всяких условий: «нет, платформа read-only. Показывается причина, время попытки и подсказка с
командой пайплайна для оператора».

Решение окончательное: **кнопки нет**. `docs/design-deviations.md` обновлён — пункт про кнопку
повтора вернулся в основную таблицу расхождений (строка 4) с этим обоснованием, а не живёт
отдельной пометкой «снято».
