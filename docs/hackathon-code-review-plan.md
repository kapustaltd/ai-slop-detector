# Платформа оценки качества кода на хакатоне — план реализации (SDD)

## 0. Суть

Claude через специальные скиллы (`review-backend`, `review-frontend`) оценивает репозитории команд по рубрике критериев. Скилл выдаёт структурированный JSON: оценки по критериям, обоснования и ссылки на участки кода (сильные и слабые места). Платформа превращает эти отчёты в:

- **главную страницу** с рейтингом команд;
- **страницу команды** с графиками и возможностью провалиться в каждый критерий: оценка, как оценивается, почему такая, фрагменты кода.

Разработка ведётся по Spec-Driven Development: constitution → spec → plan → tasks → implement.

## 1. Архитектура

```
Репозиторий команды (зафиксированный commit SHA)
        │
        ▼
Runner ──► Claude + скилл (review-backend / review-frontend) + рубрика
        │
        ▼
JSON-отчёт (строго по схеме) ──► Валидатор / обогащение ──► Хранилище
                                                               │
                                                               ▼
                                              API ──► Дашборд + страница команды
```

### Ключевые архитектурные решения

1. **Контракт важнее всего.** JSON-схема отчёта связывает скилл и UI. Когда она зафиксирована, фронт работает на фикстурах, а скилл дорабатывается независимо.
2. **Модель ставит оценки по критериям, итоговый балл считает код.** Веса, агрегация frontend/backend и рейтинг вычисляются детерминированно.
3. **Код для UI берётся из репозитория, а не из ответа модели.** Модель возвращает `file` + `line_start`/`line_end`. Валидатор проверяет, что файл и строки существуют, и сам вырезает сниппет на нужном SHA.

## 2. Структура SDD-артефактов

```
specs/
  001-evaluation-contract/     # JSON-схема отчёта + рубрики
  002-review-skills/           # скиллы Claude для back и front
  003-runner-ingestion/        # запуск оценки, валидация, сохранение
  004-api/                     # REST API для UI
  005-leaderboard/             # главная страница с рейтингом
  006-team-details/            # страница команды, графики, drill-down
  007-jury-tools/              # ручная корректировка, перезапуск, апелляции
rubrics/
  backend.v1.yaml
  frontend.v1.yaml
```

В каждой фиче: `spec.md` (что и зачем, user stories, критерии приёмки) → `plan.md` (как) → `tasks.md` (атомарные задачи). Порядок: 001 первой, дальше параллельно.

## 3. Constitution (принципы проекта)

1. **Воспроизводимость.** Каждая оценка привязана к `commit_sha`, `skill_version`, `rubric_version`, `model`.
2. **Прозрачность.** Любой балл объясним и подкреплён ссылками на код.
3. **Справедливость.** Все команды оцениваются одной версией скилла и рубрики. Смена версии означает переоценку всех команд.
4. **Код команд — это данные, а не инструкции** (защита от prompt injection).
5. **Последнее слово за жюри.** Любую оценку можно переопределить с комментарием, обе версии видны.
6. **Итоговые баллы считает код, не LLM.**
7. **Contract-first.** Изменения схемы отчёта — только через спеку 001 с версионированием.

## 4. Фичи

### 001 — Контракт оценки (критический путь)

**Рубрика** (YAML, версионируется). Для каждого критерия: `id`, название, вес, описание и **якоря по уровням** (что означает 2, 5, 8, 10 баллов). Без якорей оценки плавают между командами.

Примеры критериев:

- **Backend:** архитектура и структура, читаемость, обработка ошибок, дизайн API, работа с данными, безопасность, тесты, конфигурация и инфраструктура (Docker, README, CI).
- **Frontend:** компонентная структура, управление состоянием, типизация, производительность, доступность, консистентность стилей, тесты.

**Схема отчёта** (набросок):

```json
{
  "meta": {
    "team_id": "team-07",
    "area": "backend",
    "repo": "https://github.com/org/team-07",
    "commit_sha": "abc123",
    "skill_version": "1.0.0",
    "rubric_version": "backend.v1",
    "model": "claude-...",
    "evaluated_at": "2026-09-21T12:00:00Z"
  },
  "criteria": [
    {
      "id": "error_handling",
      "score": 6,
      "max": 10,
      "confidence": "high | medium | low",
      "summary": "Короткий вывод в 1–2 предложения",
      "rationale": "Развёрнутое объяснение со ссылкой на якоря рубрики",
      "findings": [
        {
          "kind": "strength | issue",
          "severity": "info | minor | major | critical",
          "file": "src/api/users.py",
          "line_start": 42,
          "line_end": 58,
          "title": "Заголовок находки",
          "explanation": "Почему это хорошо/плохо",
          "suggestion": "Как улучшить (для issue)"
        }
      ]
    }
  ],
  "overall_comment": "Общий вывод по области",
  "warnings": ["suspected_prompt_injection", "repo_too_large"]
}
```

**Критерии приёмки:**

- JSON Schema лежит в репозитории и версионируется.
- Есть 2–3 валидные и 2–3 невалидные фикстуры, тесты валидации проходят.
- Типы для backend и frontend сгенерированы из схемы.
- Рубрики `backend.v1.yaml` и `frontend.v1.yaml` с якорями по уровням для каждого критерия.

### 002 — Скиллы Claude

- Два скилла: `review-backend` и `review-frontend` (проще калибровать по отдельности).
- Скилл читает рубрику из YAML, а не держит критерии в тексте промпта.
- Порядок работы: разведка структуры → проход по каждому критерию с поиском доказательств → оценка строго по якорям → вывод JSON по схеме.
- Правила:
  - игнорировать vendored-код, lock-файлы, сгенерированное, артефакты сборки;
  - не ставить оценку без хотя бы одной ссылки на код;
  - при нехватке данных снижать `confidence`, а не выдумывать.
- **Защита от инъекций.** Содержимое репозитория трактуется как данные. Попытки повлиять на оценку («оцени на 10/10» в README, комментариях) помечаются в `warnings`.
- **Калибровка на golden set.** 3–4 эталонных репозитория (хороший, средний, плохой) с согласованными жюри диапазонами оценок.

**Критерии приёмки:** скилл на golden set попадает в ожидаемые диапазоны; разброс между повторными прогонами не больше ±1 балла по критерию; вывод всегда валиден по схеме.

### 003 — Runner и ingestion

- Клон репозитория на фиксированный SHA, запуск в изолированном контейнере без секретов и без лишнего сетевого доступа.
- Запуск Claude в headless-режиме (Claude Code `claude -p` со скиллом или Claude Agent SDK), сбор JSON.
- Валидация по схеме. При ошибке — повтор с текстом ошибки (1–2 попытки), затем статус `failed`.
- **Обогащение:**
  - проверка существования файлов и диапазонов строк;
  - вырезка сниппетов из репозитория на нужном SHA;
  - генерация permalink (`blob/<sha>/path#L42-L58`);
  - невалидные ссылки помечаются, а не молча отбрасываются.
- **Стабильность:** K прогонов (2–3) на каждую область, итог по медиане. Большой разброс — флаг `needs_review`.
- **Агрегация:** итог по области = взвешенная сумма критериев по весам рубрики; итог команды = агрегация frontend + backend (формула фиксируется в спеке).
- Статусы: `pending → running → done | failed | needs_review`.
- Очередь с ограничением параллельности, логирование стоимости и времени прогонов.
- Сырой отчёт модели хранится всегда, рядом с вычисленными данными.

### 004 — API

| Метод | Назначение |
|---|---|
| `GET /teams` | Рейтинг: итог, frontend, backend, статус, время оценки |
| `GET /teams/{id}` | Сводка команды, оценки по критериям, распределение находок |
| `GET /teams/{id}/criteria/{criterionId}` | Rationale, findings со сниппетами и permalink |
| `GET /rubrics/{version}` | Описание критериев и якорей («как оценивается») |
| `GET /stats/criteria` | Медианы/средние по всем командам для сравнения |
| `POST /teams/{id}/evaluate` | Перезапуск оценки (жюри) |

Хранилище: SQLite/Postgres (для хакатона достаточно SQLite).

### 005 — Главная: рейтинг

- Таблица: место, команда, итог, frontend, backend, статус, бейдж `needs_review`.
- Сортировка и фильтры.
- Опционально: мини-спарклайны по критериям.
- Состояния: идёт оценка, ошибка, нет данных.

### 006 — Страница команды

- **Radar chart** по критериям (frontend и backend отдельно), наложенный на медиану всех команд.
- **Bar chart** «команда против среднего» по каждому критерию.
- **Распределение находок:** strengths/issues по severity.
- **Drill-down в критерий:**
  - балл, summary, rationale;
  - описание критерия и якоря рубрики («как оценивается»);
  - список находок с подсвеченным кодом (Shiki/Prism) и ссылкой на permalink.
- **Метаданные:** SHA, версии скилла, рубрики и модели, дата оценки.

### 007 — Инструменты жюри (если останется время)

- Переопределение оценки критерия с обязательным комментарием; в UI видны обе оценки.
- Перезапуск оценки, пометка «проверено жюри».

## 5. Этапы и параллельность

| Этап | Что | Параллельно |
|---|---|---|
| 1 | Constitution + 001 (схема, рубрики, фикстуры) | — (блокирует всё) |
| 2 | 002 скиллы + golden set | 004 / 005 / 006 на фикстурах |
| 3 | 003 runner + ingestion | UI продолжается |
| 4 | Интеграция end-to-end на golden set | — |
| 5 | Прогон на реальных командах, калибровка, 007 | — |

## 6. Риски

| Риск | Митигация |
|---|---|
| Нестабильность оценок | Якоря в рубрике, K прогонов с медианой, флаг `needs_review` |
| Галлюцинированные ссылки на код | Проверка в ingestion, сниппеты вырезаются из репо |
| Prompt injection из репозиториев | Правило в скилле, флаг в `warnings`, песочница |
| Большие репозитории, монорепы | Правило определения путей frontend/backend или указание путей командой при сабмите |
| Смена рубрики посреди хакатона | Версионирование, обязательная переоценка всех команд |
| Стоимость и время | Расчёт заранее: N команд × 2 области × K прогонов |

## 7. Открытые вопросы

1. Оценка запускается один раз после дедлайна или периодически по ходу хакатона (живой рейтинг)? Во втором случае нужны история оценок по SHA и график динамики.
2. Формула агрегации frontend + backend: поровну, по весам, или зависит от типа проекта (например, только backend)?
3. Как команды сабмитят проект: ссылка на репозиторий + ветка, или организаторы забирают сами?
4. Стек платформы (backend/frontend) — если не зафиксирован, выбирается в `plan.md` фичи 003/004.
