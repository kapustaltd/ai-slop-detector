## Подтверждённые расхождения

1. **P1: повторное использование оценки игнорирует версии.**
   `agent/internal/pipeline/pipeline.go`, `runArea`: cache hit проверяет только `done`
   и SHA. Проверки рубрики, скилла и модели выполняются позже и обходятся при cache hit.
   В develop условие сохраняется. `bundle.go` собирает список skill versions, но
   не отвергает смешанный набор. Это нарушает принцип III конституции и позволяет
   сравнивать старые и новые оценки. Нужен полный ключ входов и проверка совместимости
   всех отчётов до формирования рейтинга, включая загруженные из state.

2. **P1: runtime Go не эквивалентен JSON Schema.**
   `contract.DecodeReport` декодирует JSON в обычные Go-поля, затем `Validate`
   проверяет значения. Отсутствующий `score` превращается в 0 и проходит; отсутствие
   обязательного `warnings` тоже проходит. Оба случая подтверждены временными
   диагностическими тестами, удалёнными после запуска. В схеме оба поля обязательны.
   Нужна проверка исходного JSON до потери информации о наличии полей и общая
   матрица принятия/отклонения для JS и Go.

3. **P1: Go-валидация весов областей неполна.**
   `rubric.Rubric.Validate` проверяет два элемента и сумму, но не ключи
   `backend`/`frontend`. Значение `{wrong_a: 0.5, wrong_b: 0.5}` принято в
   диагностическом тесте. JS использует схему и именованные поля. Также нужны
   отрицательные тесты на нечисловые конечные значения YAML и согласованность
   area_weights между обеими рубриками; эти дополнительные случаи здесь не исполнялись.

4. **P2: разные пути оценки имеют разные правила evidence.**
   `agent.Run` передаёт `LineCounts` в validator и отклоняет несуществующие ссылки.
   `pipeline.runArea` этого не делает и передаёт отчёт в enrichment с маркировкой
   ссылок. Это соответствует разным описаниям 009 и 003, но не единому поведению
   агента. В develop отдельный путь 009 удалён. Необходимо явно закрепить, что
   отклоняется с retry, а что сохраняется как invalid finding.

5. **P2: зелёный CI не подтверждает качество оценивания.**
   `scripts/test-review-skills.sh` проверяет текст скиллов через rg, но не запускает
   оценку; в текущем CI этот скрипт также не вызывается. T006 спеки 002 отмечена
   выполненной с оговоркой об отложенных sanity-прогонах. Наличие реальных результатов
   SC-002 (сильный/слабый репозиторий), SC-003 (осмысленность) и SC-005 (инъекции)
   в проверенных тестах и артефактах не установлено.

6. **P2: отрицательные фикстуры проверяют отказ, но не его причину.**
   `web/scripts/contract.mjs`, `validateAll`: файл reason.md должен существовать,
   однако любая ошибка в catch считается ожидаемым отказом. Требование 001 SC-001
   об ожидаемой причине этим не доказано. Нужны стабильный код ошибки и JSON path.

7. **P2: статус SDD не отражает реализованный объём.**
   В main у 001/004/005/006/008/009 нет plan.md и tasks.md, хотя конституция требует
   их до реализации. Для 001–006/008/009 остаётся Draft. Это не доказывает отсутствие
   человеческого ревью вне репозитория, но делает приёмку непроверяемой из истории.

8. **P2: изменения 011 расходятся с её текстом в main.**
   `4abed97` убирает обязательность operator token без изменения спеки; она по-прежнему
   требует Bearer в production. `08c2d0d` публикует завершённые прогоны, тогда как
   overview 011 запрещает менять опубликованный бандл. В develop фича снята целиком.
   Переносить исправления следует только после выбора целевой архитектуры.

## Зависимости и порядок работы агента

Здесь нужно различать зависимости фич и зависимости пакетов проекта.

Рабочий порядок фич: 001 → 002; контракт 004 зависит от 001; 003 потребляет
001 + 002 + контракт 004; 008 потребляет 001 + 004; 005/006 потребляют 004 + 008;
010 проверяет и публикует готовый продукт. Указанные в 004 потребители 005/006
не должны трактоваться как блокирующие зависимости реализации 004. Аналогично
003 ↔ 004 — связь производителя с контрактом, а не цикл обязательного завершения.
007 исключена; 009/011 определяются выбранной веткой.

Для пакетов уже есть npm ci в CI, package-lock.json, go.mod/go.sum и проверки сборки.
Отдельного гейта аудита уязвимостей зависимостей в просмотренном workflow нет;
это не утверждение о наличии уязвимостей. Lock-файлы оцениваемых команд намеренно
исключены из анализа авторского кода; это не отменяет проверку зависимостей самой платформы.

Предлагаемый единый протокол для последующих задач агента:

1. Записать базовую ветку/SHA, spec ID, FR/SC и затронутые зависимости. Проверить
   Withdrawn и наличие plan/tasks. Не переносить требования из другой ветки молча.
2. Для изменения поведения обновить спеку. Для изменения контракта соблюдать
   порядок и версионирование 001. Исправление валидатора в рамках существующей схемы
   отдельно отличать от изменения самой схемы.
3. Добавить к каждому исправляемому инварианту положительный и отрицательный пример:
   required/null, unknown/duplicate/missing metric, score/max, веса/ключи, SHA/версии,
   evidence, retry, cache invalidation, смешанный набор версий.
4. Прогонять общий корпус JSON через JS и Go. Требовать одинакового решения и
   проверять конкретную причину отказа. Проверять рубрики и их совместимость до
   обращения к модели; бандл — до публикации.
5. Для изменения скилла фиксировать skill version и результаты sanity-пары на
   фиксированных SHA, а также clean/injection-пары. Хранить model, rubric version,
   raw output и итог валидации. Не возвращать K прогонов и статистические требования,
   снятые решением `6f9d801`.
6. Для изменения пакетов проверять согласованность manifest/lock, чистую установку,
   Go modules, тесты и production build. Проверку уязвимостей выделять в отдельный
   гейт со своей политикой, а не считать её выполненной по успешной сборке.
7. Перед завершением записать «spec/FR/SC → commit → test → результат», отдельно
   указать непройденную приёмку. Отмечать Implemented/Accepted только по подтверждённым
   результатам, а не по наличию кода или галочек в tasks.

Приоритет исправлений: cache и версии → эквивалентность JS/Go → рубрики/веса →
единый evidence policy → sanity-артефакты → общий CI-гейт и актуализация SDD-статусов.
Этот протокол — предложение по результатам аудита, не внедрённый CI-механизм.

## Исправления в рабочем дереве main после аудита

Реализован первый этап для 001/003 (без изменения схемы отчёта):

- Resume проверяет отпечаток команды/repo/SHA/области/пути, скилла, модели,
  рубрики, scanner/enrichment settings. Сохранённый JSON заново проверяется;
  агрегаты пересчитываются из валидированных листьев.
- Recalculate отклоняет повреждённые отчёты и несовместимые версии/отпечаток рубрики
  до записи бандла. Старые state без отпечатка требуют нового прогона.
- До запуска провайдера проверяются рубрики, их версии и согласованность весов.
  Итог команды использует веса из рубрики вместо отдельной константы в pipeline.
- Required/null проверяются до декодирования Go-значений. Явный score=0 и warnings=[]
  принимаются. Веса обязаны быть конечными, ключи областей — backend/frontend.
- Общие 3 valid / 6 invalid фикстур теперь прогоняются также через Go.

Трассировка: 001 required/null → TestDecodeRequiredAndNullFields,
TestDecodeAcceptsExplicitZeroAndEmptyWarnings, TestSharedContractFixtures;
001 веса → TestRejectsInvalidWeightsAndScale;
003 resume/recalculate → TestRunRetriesInvalidOutputAndResumesWithoutProvider;
003 preflight → TestConfigRejectsIncompatibleRubricsBeforeProvider;
003 агрегаты → TestTeamTotalUsesRubricWeights.

Проверки после изменений: go test ./... и npm run check прошли (29 frontend tests);
после расширения сценариев recalculate повторно прошёл пакет pipeline.

Остаются отдельными задачами: запрет смешанных версий при слиянии опубликованных

длины/форматы); сравнение конкретных причин отказа общих фикстур; поведенческие
sanity-прогоны модели и CI-гейт для проверок скиллов. Завершение первого этапа
не означает устранение всех пунктов исходного аудита.
