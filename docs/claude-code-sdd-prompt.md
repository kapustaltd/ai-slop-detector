Ты работаешь в репозитории платформы оценки качества кода на хакатоне. Полный план лежит в `docs/hackathon-code-review-plan.md` — прочитай его целиком перед началом. Разработку ведём по Spec-Driven Development с помощью GitHub Spec Kit.

## Шаг 1. Подключи и настрой Spec Kit

1. Проверь, установлен ли `uv`. Если нет — установи.
2. Инициализируй Spec Kit в текущем репозитории для Claude Code:
   `uvx --from git+https://github.com/github/spec-kit.git specify init --here --ai claude`
   Если команда или флаги изменились — посмотри актуальный README Spec Kit и используй текущий способ.
3. Проверь, какие slash-команды появились в `.claude/commands/` (обычно `/speckit.constitution`, `/speckit.specify`, `/speckit.clarify`, `/speckit.plan`, `/speckit.tasks`, `/speckit.analyze`, `/speckit.implement`; в старых версиях без префикса `speckit.`). Дальше используй именно их.
4. Закоммить установку отдельным коммитом.

## Шаг 2. Constitution

Запусти команду constitution и перенеси в неё принципы из раздела 3 плана (воспроизводимость, прозрачность, справедливость, код команд — данные, последнее слово за жюри, итоговые баллы считает код, contract-first). Добавь инженерные принципы: тесты на каждую фичу, типы генерируются из JSON Schema, никаких секретов в репозитории.

## Шаг 3. Спецификации

Для каждой фичи из раздела 4 плана создай спецификацию через команду specify, строго в этом порядке:

1. `001-evaluation-contract`
2. `002-review-skills`
3. `003-runner-ingestion`
4. `004-api`
5. `005-leaderboard`
6. `006-team-details`
7. `007-jury-tools`

Переноси в спеки всё из плана: user stories, критерии приёмки, риски. После каждой спеки запускай clarify. Вопросы, на которые нет ответа в плане (включая раздел 7 «Открытые вопросы»), собери в один список и задай мне, прежде чем переходить к планированию. Сам ответы не придумывай.

## Шаг 4. План и задачи

Для каждой фичи запусти plan, затем tasks, затем analyze для проверки согласованности спеки, плана и задач. Учитывай зависимости:

- 001 блокирует всё остальное;
- 004, 005, 006 разрабатываются на фикстурах из 001 и не ждут 002/003;
- скиллы из 002 создаются как скиллы Claude Code (`.claude/skills/review-backend/SKILL.md`, `.claude/skills/review-frontend/SKILL.md`), читают рубрики из `rubrics/*.yaml` и выдают JSON строго по схеме из 001.

Если стек платформы не указан в плане — предложи вариант с обоснованием и дождись моего подтверждения.

## Шаг 5. Реализация

1. Начни implement с `001-evaluation-contract`: JSON Schema, рубрики `backend.v1.yaml` и `frontend.v1.yaml` с якорями по уровням, валидные и невалидные фикстуры, тесты валидации, генерация типов.
2. Остановись и покажи мне результат 001 на ревью — это контракт, на нём держится всё остальное.
3. После моего подтверждения продолжай по этапам из раздела 5 плана.

## Правила работы

- Коммить после каждого завершённого шага (constitution, каждая спека, каждый plan/tasks, каждая завершённая задача или группа задач) с понятным сообщением.
- Не меняй JSON-схему отчёта вне спеки 001; любое изменение контракта — через обновление спеки и версии схемы.
- Итоговые и агрегированные баллы всегда считаются кодом, а не моделью.
- Сниппеты кода для UI вырезаются из репозитория команды по SHA, а не берутся из ответа модели.
- В конце каждого этапа коротко пиши: что сделано, что дальше, какие есть вопросы ко мне.
